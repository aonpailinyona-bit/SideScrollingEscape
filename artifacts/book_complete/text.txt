47 โครงงานวิจัยนี้มีวัตถุประสงค์เพื่อศึกษาและพัฒนาเกมคอมพิวเตอร์สองมิติแนวเอาชีวิตรอดและลอบเร้น (Survival Stealth Game) โดยมุ่งเน้นการประยุกต์ใช้เทคนิคเครื่องสถานะจำกัด (Finite State Machine: FSM) ในการควบคุมสถานะของตัวละครผู้เล่นและระบบปัญญาประดิษฐ์ (Artificial Intelligence: AI) ภายในเกม เพื่อให้การทำงานของระบบมีโครงสร้างที่ชัดเจน ลดความซับซ้อนของโปรแกรม และเพิ่มประสิทธิภาพในการควบคุมพฤติกรรมของตัวละคร การพัฒนาเกมใช้โปรแกรม Unity Game Engine และเขียนโปรแกรมด้วยภาษา C# โดยนำแนวคิด FSM มาใช้เป็นโครงสร้างหลักในการจัดการสถานะของตัวละครผู้เล่น ได้แก่ การยืน การเดิน การนั่งย่อ และการหมอบคลาน ซึ่งแต่ละสถานะมีผลต่อพารามิเตอร์ภายในเกม เช่น ความเร็วในการเคลื่อนที่ ขนาดพื้นที่การชน (Collider) และระดับความดังของเสียงแบบเรียลไทม์ นอกจากนี้ได้พัฒนาระบบปัญญาประดิษฐ์ของตัวละครศัตรูให้สามารถตรวจจับผู้เล่นผ่านระบบการมองเห็นด้วยเทคนิค Raycasting และตอบสนองต่อระดับเสียงที่ผู้เล่นสร้างขึ้น.โดยทำงานร่วมกับอัลกอริทึมค้นหาเส้นทางแบบ A* (A* Pathfinding) เพื่อให้ศัตรูสามารถเคลื่อนที่หลบหลีกสิ่งกีดขวางและไล่ล่าผู้เล่นได้อย่างสมจริง ผลการดำเนินงานพบว่า การประยุกต์ใช้เทคนิค Finite State Machine ช่วยให้สามารถจัดการสถานะของตัวละครและเงื่อนไขการทำงานของระบบ AI ได้อย่างเป็นระบบ ลดความซับซ้อนของโค้ด และเพิ่มความยืดหยุ่นในการพัฒนา ซอฟต์แวร์ต้นแบบที่พัฒนาขึ้นสามารถตอบสนองต่อคำสั่งของผู้เล่นได้อย่างถูกต้อง และตัวละครศัตรูมีพฤติกรรมการไล่ล่าที่สอดคล้องกับตรรกะที่กำหนดไว้ บรรลุตามวัตถุประสงค์ของโครงงานในการประยุกต์ใช้ความรู้ด้านวิทยาการคอมพิวเตอร์เพื่อพัฒนาสื่อบันเทิงเชิงโต้ตอบ

65 โครงงานวิจัยฉบับนี้สำเร็จลุล่วงไปได้ด้วยดีเนื่องด้วยความกรุณาจาก อาจารย์ธนวัฒน์ ถาวรกูล และ ผศ.วราภรณ์ มั่นทุ่ง อาจารย์ที่ปรึกษาโครงงาน ที่ได้ให้คำปรึกษา แนะนำแนวทาง และแก้ไขข้อบกพร่องต่าง ๆ ในการพัฒนาเกมสยองขวัญ 2 มิติเชิงจริยธรรมด้วยภาษา C# ตลอดจนถ่ายทอดความรู้และเทคนิคต่าง ๆ ในการใช้โปรแกรม Unity จนโครงงานเล่มนี้เสร็จสมบูรณ์ 
66 ขอกราบขอบพระคุณบิดา มารดา และครอบครัว ที่ให้การสนับสนุนทั้งในด้านกำลังใจและทุนทรัพย์ในการศึกษาเล่าเรียนเสมอมา รวมถึงขอขอบคุณเพื่อนนักศึกษาทุกท่านที่ให้ความช่วยเหลือในการทดสอบระบบเกมและให้คำแนะนำที่เป็นประโยชน์ต่อการพัฒนาโครงงานในครั้งนี้ 
67 คุณค่าและประโยชน์ของโครงงานวิจัยฉบับนี้ ผู้จัดทำขอมอบเป็นเครื่องบูชาพระคุณบิดา มารดา ครูบาอาจารย์ และผู้มีพระคุณทุกท่านที่มีส่วนช่วยให้ผู้จัดทำประสบความสำเร็จในการศึกษา

83 1.1 ความเป็นมาและความสำคัญของปัญหา
84 การพัฒนาเกมคอมพิวเตอร์ในปัจจุบันมีความซับซ้อนทางด้านวิศวกรรมซอฟต์แวร์มากขึ้น โดยเฉพาะในเกมแนวลอบเร้น (Stealth Survival) หัวใจสำคัญไม่ได้อยู่ที่ความสวยงามเพียงอย่างเดียว แต่อยู่ที่ "การออกแบบโครงสร้างโค้ด (Software Architecture)" เพื่อควบคุมสถานะของตัวละคร (Player State Management) ที่มีความละเอียดซับซ้อน เช่น การเปลี่ยนอิริยาบถจากการยืน เป็นการนั่งย่อ หรือการหมอบคลาน ซึ่งการกระทำเหล่านี้ต้องส่งผลต่อค่าพารามิเตอร์ต่างๆ ทางฟิสิกส์และการตรวจจับภายในเกมแบบเรียลไทม์
85 นอกจากนี้ การสร้างศัตรูคอมพิวเตอร์ (AI Agent) ให้มีความฉลาดและตอบสนองต่อพฤติกรรมของผู้เล่นอย่างสมจริง จำเป็นต้องประยุกต์ใช้อัลกอริทึมขั้นสูง เช่น Finite State Machine (FSM) ในการจำแนกสถานะ และการคำนวณทางคณิตศาสตร์เวกเตอร์ (Vector Mathematics) เพื่อตรวจสอบการมองเห็น (Line of Sight) และการได้ยินเสียงที่แปรผันตามท่าทางของผู้เล่น
86 ผู้จัดทำจึงมีแนวคิดพัฒนาโครงงาน "การพัฒนาเกมโดยประยุกต์ใช้เทคนิค Finite State Machine ในการควบคุมตัวละครและปัญญาประดิษฐ์" โดยใช้ Unity Game Engine และภาษา C# โครงงานนี้จะมุ่งเน้นการเขียนโปรแกรมเพื่อจัดการกลไกการเคลื่อนไหวที่ซับซ้อน (Advanced Movement Mechanics) และระบบ AI ที่ไล่ล่าผู้เล่นอย่างเป็นระบบ เพื่อเป็นกรณีศึกษาการนำความรู้วิทยาการคอมพิวเตอร์มาประยุกต์ใช้ในการสร้างซอฟต์แวร์ที่มีการโต้ตอบสูง
87 1.2 วัตถุประสงค์ของโครงงาน
88 1.2.1 เพื่อพัฒนาเกมคอมพิวเตอร์ 2 มิติ ด้วยภาษา C# โดยเน้นการวางโครงสร้างโค้ดแบบเชิงวัตถุ (Object-Oriented Programming)
89 1.2.2 เพื่อประยุกต์ใช้โครงสร้างข้อมูลแบบ Finite State Machine (FSM) ในการจัดการสถานะการเคลื่อนไหวของตัวละครผู้เล่น (Movement States
90 1.2.3 เพื่อพัฒนาอัลกอริทึมปัญญาประดิษฐ์ (AI) สำหรับศัตรูที่สามารถตอบสนองต่อระดับเสียงและขนาดพื้นที่การมองเห็น (Hitbox) ที่เปลี่ยนแปลงไปตามสถานะของผู้เล่นได้
91 1.2.4 เพื่อสร้างระบบการเล่น (Gameplay Loop) ที่สมบูรณ์ ทั้งการเก็บไอเทม การแก้ไขปริศนา และการเปลี่ยนฉากเมื่อผ่านเงื่อนไข
92 1.2.5 เพื่อประเมินความพึงพอใจของผู้เล่นต่อเกมที่พัฒนาขึ้น เพื่อนำไปปรับปรุงและพัฒนาระบบให้มีประสิทธิภาพยิ่งขึ้น
93 1.3 ขอบเขตของโครงงาน
94 	1.3.1 ส่วนพัฒนาระบบควบคุมตัวละคร (Player Controller System)
95 พัฒนาระบบควบคุมตัวละครผู้เล่นให้สามารถเคลื่อนไหวได้หลากหลายรูปแบบ และส่งผลต่อการเล่นในเชิงกลยุทธ์ เช่น การลดเสียงเพื่อหลบศัตรู
96 1.3.1.1 State Management 
97 	พัฒนาระบบสถานะของตัวละครโดยใช้ Finite State Machine (FSM) เพื่อควบคุมการเปลี่ยนสถานะระหว่าง Idle, Walk, Crouch และ Prone อย่างเป็นลำดับ
98 1.3.1.2 Dynamic Collider Adjustment 
99 	พัฒนาระบบปรับขนาด Hitbox ตามท่าทางของตัวละครแบบเรียลไทม์ เพื่อรองรับการเคลื่อนที่ในพื้นที่จำกัด เช่น การหมอบลอดช่องแคบ
100 1.3.1.3 Variable Parameters 
101 		กำหนดค่าความเร็วและระดับเสียงในแต่ละสถานะ เพื่อใช้เป็นข้อมูลในการตรวจจับของศัตรู
102 1.3.2 ส่วนพัฒนาระบบปัญญาประดิษฐ์ของศัตรู (Enemy AI System)
103 		พัฒนาระบบ AI ที่สามารถตอบสนองต่อพฤติกรรมของผู้เล่น โดยเน้นการตรวจจับและการตัดสินใจแบบเรียลไทม์
104 1.3.2.1 Behavior System (FSM) 
105 	กำหนดสถานะของศัตรู เช่น Patrol, Investigate, Chaseและ Attack เพื่อควบคุมพฤติกรรม
106 1.3.2.2 Sensory System 
107 		พัฒนาระบบการมองเห็นด้วย Raycasting และระบบการได้ยินโดยใช้การคำนวณระยะทางร่วมกับระดับเสียงของผู้เล่น
108 1.3.2.3 Pathfinding 
109 	ใช้ Navigation Mesh และ A* Algorithm เพื่อให้ศัตรูสามารถเคลื่อนที่หลบสิ่งกีดขวางและติดตามผู้เล่นได้
110 1.3.3 ส่วนพัฒนาระบบเกม (Game Logic System) 
111 		พัฒนากลไกหลักของเกมเพื่อกำหนดเป้าหมายและลำดับการเล่น
112 1.3.3.1 Inventory และ Mission Logic 
113 			ผู้เล่นต้องเก็บไอเทมให้ครบจำนวนที่กำหนด (เช่น 5 ชิ้น) เพื่อปลดล็อกทางออก
114 1.3.3.2 Scene Management 
115 	รองรับการเปลี่ยนฉากและการเก็บข้อมูลความคืบหน้าของเกม
116 	1.3.4 ส่วนออกแบบส่วนติดต่อผู้ใช้งาน (UI/UX) 
117 		เป็นการออกแบบส่วนติดต่อผู้ใช้เพื่อแสดงข้อมูลสำคัญ เช่น สถานะตัวละคร ระดับเสียง และจำนวนไอเทม เพื่อช่วยให้ผู้เล่นสามารถวางแผนการเล่นและตัดสินใจได้อย่างมีประสิทธิภาพ
118 1.3.5 ขอบเขตด้านเนื้อหาเกม (Game Content Scope)
119 	1.3.5.1 เกมที่พัฒนาเป็นเกมคอมพิวเตอร์แบบ 2 มิติ แนวลอบเร้น (Stealth Gameโดยผู้เล่นต้องหลบหลีกศัตรูและวางแผนการเคลื่อนที่
120 	1.3.5.2 ภายในเกมมีฉากการเล่นอย่างน้อย 1–2 ฉาก ซึ่งออกแบบให้มีสิ่งกีดขวางและพื้นที่สำหรับการหลบซ่อน
121 	1.3.5.3 มีตัวละครศัตรูอย่างน้อย 1 ประเภท ที่สามารถลาดตระเวน ตรวจจับเสียง และไล่ล่าผู้เล่นได้
122 1.3.5.4 มีระบบการเก็บไอเทม โดยผู้เล่นต้องรวบรวมไอเทมให้ครบตามจำนวนที่กำหนด
123 เพื่อผ่านด่าน
124 		1.3.5.5 มีเงื่อนไขการชนะ (Win Condition) เมื่อผู้เล่นเก็บไอเทมครบและไปถึงทางออกของฉาก
125 1.3.5.6 มีเงื่อนไขการแพ้ (Lose Condition) เมื่อผู้เล่นถูกศัตรูตรวจจับและพลังชีวิหมด

161 2.1 แนวคิดเกี่ยวกับการพัฒนาเกม (Game Development)
162 การพัฒนาเกม (Game Development) เป็นกระบวนการสร้างซอฟต์แวร์ เชิงโต้ตอบที่ผสานองค์ประกอบด้านการออกแบบ ศิลปะ และวิศวกรรมซอฟต์แวร์เข้าด้วย กัน โดยทั่วไปกระบวนการพัฒนาเกมประกอบด้วยขั้นตอนการวิเคราะห์ความต้องการ (Requirement Analysis) การออกแบบระบบ (System Design) การพัฒนา (Implementation) การทดสอบ (Testing) และการประเมินผล (Evaluation) กระบวนการสร้างเกม (Game Development) คือ กระบวนการในมุมมอง ของการสร้างการออกแบบ โดยใช้ประกอบในมุมมองสองมิติ โดยการออกประกอบจาก เกม X (แนวนอน) และแนวนอน Y (แนวตั้ง) ซึ่งแตกต่างจากเกม 3 มิติที่สามารถแสดง ตัวละครจากเกม ในการรวมกันสร้างสรรค์เกมในการออกแบบ เกม 2 มิติจะดำเนินการใน พื้นที่ หรือสิ่งต่างๆ ในการออกแบบ ทั้งนี้ เกม 2 มิติที่มีสามารถแสดงสถานการณ์สำหรับผู้ เล่นในเนื้อหาหรืออาจจะใช้ในการออกแบบแนวเกมสนุก ที่ตัวละครจะสร้างสรรค์กลยุทธ์ และสามารถสร้างความประทับใจให้ผู้เล่นได้ องค์ประกอบสำคัญของเกม ได้แก่ ระบบกลไกการเล่น (Game Mechanics) ระบบกราฟิกและแอนิเมชัน ระบบเสียง ระบบปัญญาประดิษฐ์ (AI System) และส่วน ติดต่อผู้ใช้ (User Interface) ในเกมที่มีศัตรูหรือ NPC ระบบ AI มีบทบาทสำคัญใน การสร้างความท้าทายและความสมจริง โดยเฉพาะเกมแนวสยองขวัญ (Horror Game) ที่พฤติกรรมของศัตรูต้องตอบสนองต่อการกระทำของผู้เล่นอย่างมีเหตุผล
163 2.2 การพัฒนาเกม 2 มิติ
164 การพัฒนาเกม 2 มิติ (2D Game Development) เป็นการสร้างเกมที่ใช้ พิกัดสองมิติในการแสดงผล ประกอบด้วยแกน X (แนวนอน) และแกน Y (แนวตั้ง) ซึ่ง แตกต่างจากเกม 3 มิติที่มีความลึก (Depth) เพิ่มเติม เกม 2 มิติมีความได้เปรียบใน ด้านความง่ายต่อการพัฒนา สุนทรียศาสตร์ที่มีเอกลักษณ์ได้ ใช้ทรัพยากรการประมวลผลต่ำกว่า และสามารถสร้าง นักพัฒนาจะต้องออกแบบและควบคุมสภาพแวดล้อม โดยระบบดำเนินการเส้นทาง (Platformer) ร่วมลักษณะการทำงานในสามารถทำงานได้ดีในเกม 2 มิติ โดยแตก ต่างจากเกม 3 มิติในด้านความซับซ้อน ในการพัฒนาเกม 2 มิติ เครื่องมือที่นิยมใช้คือUnity Game Engine ซึ่งรองรับการพัฒนาเกม 2 มิติได้อย่างครบถ้วน ทั้งระบบ Sprite, Tilemaps, Physics 2D และ Animator สำหรับการสร้างแอนิเมชั่นตัว ละคร ส่วนสำคัญที่สำคัญในการพัฒนาเกม 2 มิติ คือการออกแบบระดับ (Level Design) ซึ่งเป็นการเลือกรูปแบบและทรัพยากรในการพัฒนาเกม รวมถึงการออกแบบ Tilemap เพื่อสร้างฉากที่มีความสวยงามและน่าสนใจ นอกจากนี้ระบบ Collision Detection ก็มีความสำคัญในการตรวจจับการชนระหว่างตัวละครกับสิ่งแวดล้อม ภายในเกม
165 2.3 เกม Side-scrolling game หรือ Side-view game
166 เกม Side-scrolling game หรือ Side-view game คือเกมที่มุมกล้อง ถูกกำหนดให้มองจากด้านข้างของตัวละคร ทำให้ผู้เล่นเห็นตัวละครในแนวตั้งและสามารถ เคลื่อนที่ไปทางซ้ายหรือขวาตามแกน X เป็นหลัก มุมมองแบบนี้เป็นที่นิยมอย่างกว้างขวางในเกมยุคแรก ๆ และยังคงได้รับความนิยมอย่างต่อเนื่องในเกมยุคปัจจุบัน เนื่องจาก สามารถสร้างประสบการณ์การเล่นที่ชัดเจนและเข้าใจง่าย คุณลักษณะสำคัญของเกม Side-scrolling ได้แก่ การเคลื่อนที่ของตัวละครใน แนวแกน X เป็นหลัก กล้องจะเลื่อนตาม (Follow Camera) ไปพร้อมกับตัวละคร การออกแบบฉากในแนวนอนที่มีความต่อเนื่อง รวมถึงการใช้ระบบชั้น (Layering) เพื่อสร้างความลึกในภาพแบบ 2 มิติ เช่น ฉากหลังเลื่อนช้ากว่าฉากหน้า (Parallax Scrolling) ซึ่งช่วยเพิ่มความสมจริงให้กับเกม ในการพัฒนาเกม Side-scrolling Horror Game นั้น มุมมองด้านข้างช่วย สร้างบรรยากาศความหวาดกลัวได้อย่างมีประสิทธิภาพ เนื่องจากผู้เล่นจะมองเห็นสิ่งที่อยู่ ข้างหน้าและข้างหลังได้อย่างชัดเจน แต่ไม่สามารถมองเห็นสิ่งที่อยู่ด้านบนหรือด้านล่างได้ ครบถ้วน ทำให้เกิดความตื่นเต้นและความไม่แน่นอนขณะเล่น

170 2.4 เกมประเภท Hide-and-Seek Horror Game
171 เกมประเภท Hide-and-Seek Horror Game คือเกมสยองขวัญที่มีแกน หลักของการเล่น (Core Gameplay) อยู่ที่การหลบซ่อนตัวจากศัตรูหรือผู้ไล่ล่า (Pursuer) ผู้เล่นจะต้องใช้ไหวพริบและความระมัดระวังในการหลบหลีกศัตรู รวบรวม ไอเทมที่กำหนด และหาทางออกจากด่านให้สำเร็จ โดยไม่ถูกศัตรูจับได้ เกมประเภทนี้มีชื่อเสียงเช่น Slender: The Eight Pages, Outlast, และ Amnesia: The Dark Descent  องค์ประกอบสำคัญของ Hide-and-Seek Horror Game ได้แก่ ระบบ ตรวจจับของศัตรู (Enemy Detection System) ซึ่งประกอบด้วยการมองเห็น (Line of Sight) และการได้ยินเสียง (Sound Detection) ผู้เล่นจะต้องควบคุม ระดับเสียงที่เกิดจากการเคลื่อนไหว เช่น การเดินธรรมดาจะมีเสียงดังกว่าการนั่งย่อหรือหมอบคลาน รวมถึงการใช้สภาพแวดล้อม เช่น การซ่อนตัวในตู้หรือใต้โต๊ะ เพื่อหลบเลี่ยง การตรวจจับในเกม 2 มิติแนว Side-scrolling Horror Game การออกแบบระบบ Al ของศัตรูมีความสำคัญอย่างยิ่ง ศัตรูจะต้องมีพฤติกรรมที่สมเหตุสมผลและน่าเชื่อถือ โดย อาศัยเทคนิค Finite State Machine (FSM) ในการจัดการสถานะพฤติกรรมต่าง ๆ เช่น การลาดตระเวน การตรวจสอบเสียง และการไล่ล่า รวมถึงระบบ Raycasting สำหรับตรวจสอบการมองเห็น และอัลกอริทึม A* สำหรับการนำทางในฉาก
172 2.5 แนวคิดเกี่ยวกับ Finite State Machine (FSM)
173 Finite State Machine (FSM) หรือเครื่องสถานะจำกัด เป็นแบบจำลอง และการ การคำนวณที่ใช้กำหนดพฤติกรรมของระบบผ่านชุดของสถานะ (States) เปลี่ยนผ่านสถานะ (Transitions) ตามเงื่อนไขที่กำหนด โดยในช่วงเวลาใดเวลาหนึ่ง ระบบจะอยู่ได้เพียงสถานะเดียวเท่านั้น FSM เป็นที่นิยมอย่างกว้างขวางในการพัฒนาเกม เนื่องจากเข้าใจง่าย ใช้ทรัพยากรประมวลผลต่ำ และสามารถปรับแก้พฤติกรรมได้โดยไม่ กระทบโครงสร้างทั้งหมด
174 องค์ประกอบหลักของ FSM ได้แก่ สถานะเริ่มต้น (Initial State) สถานะการ ทำงาน (Operational States) เหตุการณ์หรือเงื่อนไข (Event/Condition) การเปลี่ยนสถานะ (Transition) และการกระทำภายในสถานะ (State Action) ใน โครงงานนี้ FSM ถูกนำมาใช้ควบคุมทั้งตัวละครผู้เล่นและ Al ของศัตรู สำหรับตัวละครผู้เล่นใน Hide-and-Seek Horror Game สถานะที่ใช้ใน FSM ได้แก่ การยืนเดิน (Walk) ความเร็วปกติและรัศมีเสียงกว้าง การนั่งย่อ(Crouch) ความเร็วลดลงและรัศมีเสียงปานกลาง และการหมอบคลาน (Prone) ความเร็วต่ำที่สุดและรัศมีเสียงเงียบที่สุด แต่ละสถานะส่งผลต่อขนาด Collider และ ระดับ Noise Radius ซึ่งเป็นปัจจัยหลักในการถูกตรวจจับโดย A สำหรับ Al ของศัตรู (Ghost/Killer) สถานะที่ใช้ใน FSM ได้แก่ Patrol State (ลาดตระเวนตาม Waypoints), Investigate State (ตรวจสอบจุดที่ ได้ยินเสียง), Chase State (ไล่ล่าเมื่อเห็นผู้เล่นใน Vision Cone) และ Attack State (โจมตีเมื่อระยะห่าง ≤ 2 pixel) นอกจากนี้ FSM ยังกล่าวถึง Hierarchical Finite State Machine (HFSM) ซึ่งเป็นการจัดลำดับชั้นของสถานะเพื่อลดความ ซับซ้อนของ FSM แบบดั้งเดิม ทำให้สามารถบริหารจัดการพฤติกรรมที่ซับซ้อนได้ดียิ่งขึ้น
175 2.6 การพัฒนาปัญญาประดิษฐ์ในเกม
176 Game Al (Game Artificial Intelligence) หมายถึง ระบบที่ควบคุม พฤติกรรมของตัวละครในเกมให้สามารถโต้ตอบกับผู้เล่นได้อย่างสมเหตุสมผล เป้าหมาย หลักของ Game Al ไม่ใช่การเรียนรู้ชั้นสูงแบบ Machine Learning แต่เป็นการ สร้าง "ภาพลวงตาของความฉลาด" เพื่อเพิ่มความสนุกและความท้าทายในการเล่น เทคนิคที่นิยมใช้ใน Game Al ได้แก่ Rule-based System, Finite State Machine (FSM), Behavior Tree และ Pathfinding Algorithm ในเกม 2 มิติแนว Hide-and-Seek Horror Game ระบบ Al ของศัตรูจำเป็นต้อง ผสมผสานเทคนิคหลายอย่างเข้าด้วยกัน ดังนี้
177 	2.6.1 Finite State Machine (FSM) สำหรับศัตรู ใช้ FSM ในการจัดการสถานะพฤติกรรมของศัตรู (Ghost/Killer Al) โดยแบ่ง ออกเป็นสถานะ Patrol, Investigate, Chase และ Attack โดยแต่ละ สถานะจะเปลี่ยนไปตามเงื่อนไขที่ตรวจจับได้จากสภาพแวดล้อม เช่น ระยะสายตา และระดับเสียงของผู้เล่น 
178 	2.6.2 Sensory System (ระบบการรับรู้) พัฒนาระบบรับรู้ของ Al โดยใช้ Raycasting ในการจำลองสายตา (Line of Sight / Vision Cone) เพื่อตรวจสอบว่าผู้เล่นอยู่ในแนวสายตาของศัตรูหรือไม่ และใช้การคำนวณระยะทาง (Distance Check) เปรียบเทียบกับ Noise Radius ที่ผู้เล่นสร้างขึ้นตามท่าทางการเคลื่อนไหว 			
179 	2.6.3 การค้นหาเส้นทาง ใช้ระบบ Navigation ร่วมกับ A* Algorithm ให้ Al สามารถเดินไล่ล่าผู้เล่น หลบสิ่งกีดขวาง และเคลื่อนที่ไปยังจุดที่ได้ยินเสียงล่าสุดได้อย่างสมจริงภายในฉาก เกม 2 มิติแนว Side-scrolling
180 2.7 ภาษาและเครื่องมือที่ใช้พัฒนา
181 	2.7.1 Visual Studio Code
182 		เป็นโปรแกรมแก้ไขโค้ด (Code Editor) ที่พัฒนาโดย Microsoft มีความ ยืดหยุ่นสูง รองรับภาษาโปรแกรมต่างๆ ด้วยส่วนขยาย (Extensions) ที่หลาก หลาย สามารถเชื่อมต่อกับภาษา C# และ Unity Game Engine ได้อย่าง สะดวก มีระบบ IntelliSense ช่วยแนะนำโค้ดและแก้ไขข้อผิดพลาดได้อย่างมี ประสิทธิภาพ
183 	2.7.2 เอ็นจิ้นเกม Unity
184 		เป็นแอปพลิเคชันสำหรับการพัฒนาเกม มีความยืดหยุ่นสูง รองรับการพัฒนาเกมทั้ง 2 มิติ และ 3 มิติ โดยสามารถส่งออกเกมไปยัง Windows, Android และ iOS ได้อย่างสะดวก Unity มีเครื่องมือสำคัญดังนี้
185 		2.7.2.1 Scene Editor ใช้ในการออกแบบฉากและจัดวางวัตถุใน เกม รวมถึงการสร้าง Tilemap สำหรับเกม 2 มิติแนว Side-scrolling 
186 		2.7.2.2 Animator ใช้ควบคุมและแสดงผลแอนิเมชันของตัวละครใน สถานะต่าง ๆ เช่น Walk, Crouch, Prone
187 		 2.7.2.3 Physics Engine 2D จัดการระบบฟิสิกส์ การชน (Collision) และการเคลื่อนที่ของวัตถุในเกม 2 มิติ
188 	2.7.3 ภาษาโปรแกรม C#
189 		เป็นภาษาหลักที่ใช้ในการพัฒนาเกมใน Unity มีโครงสร้างเชิงวัตถุ (OOP) ที่ ชัดเจน รองรับการสร้างระบบที่ซับซ้อน เช่น ระบบ FSM ระบบ AI ระบบ Inventory และการจัดการสถานะตัวละคร โดยในโครงงานนี้ใช้ C# เขียน สคริปต์ควบคุมการทำงานทั้งหมด
190 		2.7.3.1 Game Logic Scripting สำหรับเขียนตรรกะการทำงาน ของระบบต่าง ๆ เช่น การเปลี่ยนสถานะ FSM และการตรวจจับ 
191 		2.7.3.2 Event Handling ใช้จัดการเหตุการณ์ต่าง ๆ เช่น Input ของผู้เล่น การชน และการเปลี่ยนฉาก
192 		 2.7.3.3 Data Management ใช้จัดการข้อมูลไอเทม สถานะผู้เล่น และการส่งต่อข้อมูลข้ามฉาก (Data Persistence)
193 	2.7.4 JSON (JavaScript Object Notation)
194 		เป็นรูปแบบไฟล์ข้อมูลที่มีโครงสร้างแบบคู่ระหว่างชื่อ (Key) และค่า (Value) ซึ่งอ่านและแก้ไขได้ง่ายในรูปแบบ Human-Readable Format สามารถใช้ ร่วมกับภาษา C# ใน Unity เพื่อบันทึกและโหลดข้อมูลเกม เช่น ข้อมูลตัวละคร และความคืบหน้าในการเล่น
195 2.8 อัลกอริทึมการค้นหาเส้นทาง (Pathfinding Algorithm)
196 ระบบค้นหาเส้นทาง (Pathfinding) มีบทบาทสำคัญในการทำให้ Al ของศัตรู สามารถเคลื่อนที่ภายในฉากเกม 2 มิติ Side-scrolling ได้อย่างมีประสิทธิภาพและ หลบหลีกสิ่งกีดขวางต่าง ๆ ได้อย่างสมจริง A* Algorithm (A-Star) เป็นอัลกอริทึมที่นิยมใช้ในเกม เนื่องจากสามารถ คำนวณเส้นทางที่เหมาะสมที่สุดโดยพิจารณาทั้งค่าใช้จ่ายจริงจากจุดเริ่มต้น (g-cost) และค่าประมาณระยะทางไปยังเป้าหมาย (h-cost) โดย f(n) = g(n) + h(n) ทำให้ ได้เส้นทางที่สั้นที่สุดในเวลาอันรวดเร็ว การทำงานร่วมกันระหว่าง FSM และ A* ใน Hide-and-Seek Horror Game มีลักษณะดังนี้ เมื่อ FSM ของศัตรูเปลี่ยนเป็นสถานะ Investigate ระบบจะ เรียกใช้ A* เพื่อนำทางไปยังตำแหน่งที่ได้ยินเสียงล่าสุด และเมื่อเปลี่ยนเป็นสถานะ Chase ระบบจะคำนวณเส้นทางไปยังตำแหน่งปัจจุบันของผู้เล่นแบบเรียลไทม์ โครงสร้างนี้ช่วยให้ศัตรูมีพฤติกรรมการไล่ล่าที่สมจริงและน่าตื่นเต้นยิ่งขึ้น
197 การออกแบบ UX/UI ให้เหมาะสม
198 การออกแบบส่วนติดต่อผู้ใช้ (User Interface: UI) และประสบการณ์ผู้ใช้ (User Experience: UX) เป็นองค์ประกอบสำคัญในการพัฒนาเกมที่ช่วยให้ผู้เล่น สามารถโต้ตอบกับระบบได้อย่างสะดวกและเข้าใจง่าย ในเกม 2 มิติ Side-scrolling Hide-and-Seek Horror Game การออกแบบ UI ที่ดีจะต้องไม่บดบังทัศนวิสัย ของผู้เล่น แต่ยังคงสื่อสารข้อมูลสำคัญได้อย่างชัดเจน องค์ประกอบ UI ที่สำคัญในเกมประเภทนี้ ได้แก่ ตัวบ่งชี้ท่าทาง (Stance Indicator) ที่แสดงสถานะปัจจุบันของผู้เล่นว่ากำลังยืน นั่งย่อ หรือหมอบคลาน มิเตอร์ เสียง (Noise Meter) ที่แสดงระดับความดังของเสียงที่ผู้เล่นสร้างขึ้นแบบเรียลไทม์ พลังชีวิต (HP Bar) และตัวนับไอเทม (Item Counter) เพื่อให้ผู้เล่นทราบความคืบ หน้าของภารกิจ หลักการออกแบบ UX ที่ดีในเกม Horror คือการใช้สีและเสียงเพื่อสร้าง บรรยากาศความกลัว โดยไม่ทำให้ UI ดูไม่สอดคล้องกับโทนของเกม นอกจากนี้ควร ออกแบบ HUD (Head-Up Display) ที่กระชับ สื่อความหมายได้ชัดเจน และตอบ สนองต่อสถานการณ์ในเกมได้อย่างทันท่วงที และน่าตื่นเต้น เพื่อสร้างประสบการณ์การเล่นที่น่าจดจำและน่าตื่นเต้น
199 2.10 งานวิจัยที่เกี่ยวข้อง
200 	2.10.1 Finite State Machine in Game Development
201 		งานวิจัยนี้ศึกษาแนวคิดและหลักการทำงานของ Finite State Machine (FSM) ในการพัฒนาระบบปัญญาประดิษฐ์ (AI) สำหรับควบคุมพฤติกรรมของตัวละครที่ไม่ใช่ผู้เล่น (Non-Player Characters: NPC) ภายในเกม โดยอธิบายว่า FSM เป็นแบบจำลองที่ประกอบด้วย “สถานะ (State)” และ “การเปลี่ยนสถานะ (Transition)” ซึ่งจะเปลี่ยนไปตามเงื่อนไขที่กำหนดไว้ล่วงหน้า การประยุกต์ใช้ FSM ในเกมช่วยให้สามารถกำหนดพฤติกรรมของตัวละคร เช่น การเดิน การไล่ล่า การโจมตี การป้องกัน หรือการหลบหนี ได้อย่างเป็นระบบ ลดความซับซ้อนของโค้ด และเพิ่มความชัดเจนในการออกแบบระบบ นอกจากนี้ งานวิจัยยังกล่าวถึง Hierarchical Finite State Machine (HFSM) ซึ่งเป็นการจัดลำดับชั้นของสถานะเพื่อลดความซับซ้อนของ FSM แบบดั้งเดิม ทำให้สามารถบริหารจัดการพฤติกรรมที่ซับซ้อนได้ดียิ่งขึ้น ผลการศึกษาสรุปว่า FSM เป็นเทคนิคที่มีประสิทธิภาพ เข้าใจง่าย และยังคงได้รับความนิยมในการพัฒนาเกมสมัยใหม่
202 	2.10.2 Development of Two Dimension (2D) Game Engine with Finite State Machine (FSM) Based Artificial Intelligence (AI) Subsystem
203 		งานวิจัยนี้มุ่งพัฒนาเกมเอนจินแบบ 2 มิติ ที่มีระบบ AI ภายในโดยใช้แนวคิด FSM เป็นแกนหลักของการควบคุมพฤติกรรมตัวละคร พัฒนาด้วยเทคโนโลยีเว็บ เช่น JavaScript และ WebGL 2.0 มีการเปรียบเทียบประสิทธิภาพระหว่างการพัฒนา AI แบบทั่วไป (Naive Approach) กับการใช้ FSM เป็นโครงสร้างหลัก พบว่า การใช้ FSM สามารถรักษาค่าเฟรมเรต (Frames Per Second: FPS) ได้ที่ประมาณ 60 FPS ขณะที่วิธีทั่วไปทำให้เฟรมเรต ลดลงเหลือประมาณ 50 FPS แสดงให้เห็นว่า FSM ช่วยเพิ่มประสิทธิภาพของระบบ ลดความกำกวมของตรรกะการทำงาน และช่วยให้การจัดการพฤติกรรมของตัวละครเป็นระบบมากขึ้น
204 	2.10.3 An Analysis of Finite State Machine Based Enemy Artificial Intelligence in Kirby: Nightmare in Dream Land
205 		บทความนี้ศึกษาการประยุกต์ใช้เทคนิค Finite State Machine (FSM) ในการออกแบบปัญญาประดิษฐ์ของศัตรูในเกม Kirby: Nightmare in Dream Land โดยมุ่งวิเคราะห์ว่าโครงสร้างแบบกำหนดสถานะสามารถควบคุมพฤติกรรมศัตรูและส่งผลต่อระดับความยากของเกมได้อย่างไร ผู้วิจัยอธิบายว่า FSM เป็นโมเดลที่แบ่งพฤติกรรมออกเป็นสถานะต่าง ๆ เช่น หยุดนิ่ง (Idle) เดินลาดตระเวน (Patrol) โจมตี (Attack) ถูกโจมตี (Hit) และฟื้นตัว (Recover) และกำหนดเงื่อนไขการเปลี่ยนสถานะอย่างชัดเจนตามเหตุการณ์ที่เกิดขึ้นในเกม จากการทดลองสังเกตพฤติกรรมศัตรูหลายครั้ง พบว่าสถานะการโจมตีมีสัดส่วนเวลามากที่สุด ขณะที่สถานะหยุดนิ่งและเดินช่วยสร้างจังหวะพักให้ผู้เล่น ทำให้เกมมีความสมดุล ไม่ยากหรือไม่ง่ายเกินไป นอกจากนี้ ผู้วิจัยยังทดลองปรับค่าระยะเวลาหน่วงก่อนการโจมตี (Attack Cooldown) และพบว่ายิ่งศัตรูโจมตีถี่ขึ้น ระดับความยากของเกมก็เพิ่มสูงขึ้นอย่างชัดเจน แสดงให้เห็นว่า FSM สามารถปรับความท้าทายของเกมได้โดยการแก้ไขพารามิเตอร์เพียงบางค่า โดยไม่ต้องปรับโครงสร้าง AI ทั้งระบบ โดยสรุป งานวิจัยชี้ให้เห็นว่า FSM เป็นเทคนิคที่มีความเสถียร ใช้ทรัพยากรประมวลผลต่ำ ควบคุมและปรับแต่งได้ง่าย และยังคงมีความเหมาะสมสำหรับการพัฒนา AI ในเกมแพลตฟอร์ม 2 มิติ แม้จะมีเทคนิค AI ที่ซับซ้อนกว่าพัฒนาขึ้นในปัจจุบันก็ตาม
206 	2.10.4 การออกแบบเกมดิจิทัล
207 		งานวิจัยนี้นำเสนอแนวคิดและกระบวนการออกแบบเกมดิจิทัล โดยกล่าวถึงหลักการออกแบบจากหลากหลายแนวทาง เช่น การออกแบบจากนวัตกรรม ความคิดสร้างสรรค์ เรื่องราว ความต้องการของผู้เล่น และข้อจำกัดด้านเทคโนโลยี นอกจากนี้ยังกล่าวถึงประเภทของเกม เช่น เกม 2 มิติ และ 3 มิติ รวมถึงการแบ่งตามลักษณะการเล่น เช่น เกมต่อสู้ เกมยิง เกมผจญภัย และเกมการศึกษา พร้อมทั้งเสนอขั้นตอนการพัฒนาเกมอย่างเป็นระบบ ได้แก่ การวางแผน การจัดทำเอกสารออกแบบเกม (Game Design Document: GDD) การพัฒนาโปรแกรม การสร้างวัตถุในเกม การทดสอบ และการเผยแพร่ ซึ่งเป็นแนวทางสำคัญในการพัฒนาเกมให้ประสบความสำเร็จ
208 	2.10.5 การพัฒนาเกมเพื่อการเรียนรู้การเขียนโปรแกรมภาษา C# ด้วยเกมการผจญภัยของอาเรียกับเวทย์มนต์แห่ง C#
209 		งานวิจัยนี้มีวัตถุประสงค์เพื่อพัฒนาเกมสำหรับเสริมการเรียนรู้การเขียนโปรแกรมภาษา C# โดยใช้โปรแกรม Unity ในการพัฒนาเกมแนวผจญภัย (Adventure Game) และใช้แนวคิด Game-Based Learning เพื่อให้ผู้เรียนเรียนรู้ผ่านการเล่นเกม ผลการประเมินโดยผู้เชี่ยวชาญจำนวน 5 คน พบว่าคุณภาพของเกมอยู่ในระดับดีมาก (ค่าเฉลี่ย 4.71) และเมื่อนำไปทดลองกับกลุ่มตัวอย่างจำนวน 20 คน พบว่าคะแนนหลังเรียนเพิ่มขึ้นร้อยละ 40.92 แสดงให้เห็นว่าเกมสามารถช่วยเพิ่มความเข้าใจในการเขียนโปรแกรม และส่งเสริมการคิดอย่างเป็นระบบได้อย่างมีประสิทธิภาพ
210 	2.10.6 A Systematic Review and Analysis of Intelligence-Based Pathfinding Algorithms in the Field of Video Games
211 		งานวิจัยนี้นำเสนอการทบทวนและวิเคราะห์อัลกอริทึมการค้นหาเส้นทาง (Pathfinding Algorithm) ที่ใช้ปัญญาประดิษฐ์ในเกมวิดีโอ โดยจำแนกอัลกอริทึมออกเป็น 3 กลุ่มหลัก ได้แก่ กลุ่ม Uninformed Search เช่น BFS และ Dijkstra's กลุ่ม Informed Search เช่น A* และ Greedy Best First และกลุ่ม Metaheuristic เช่น Genetic Algorithm และ Ant Colony Optimization ผู้วิจัยได้ทดสอบอัลกอริทึมบน Grid 2 มิติขนาด 4×4, 8×8, 16×16 และ 32×32 โดยใช้ Unity Game Engine เป็นสภาพแวดล้อมในการทดสอบ วัดผลด้วยเวลาประมวลผล (Execution Time) จำนวนบล็อกที่ผ่าน และความยาวเส้นทางที่สั้นที่สุด ผลการทดลองพบว่า A* Algorithm มีความสมดุลระหว่างความเร็วและความแม่นยำสูงที่สุด โดยใช้เวลาประมวลผลน้อยกว่า Dijkstra's และ BFS ในทุกขนาด Grid ทั้งที่มีและไม่มีสิ่งกีดขวาง และยังรับประกันเส้นทางที่สั้นที่สุด ซึ่งต่างจาก Greedy Best First ที่แม้จะเร็วที่สุดแต่ไม่ให้เส้นทางที่เหมาะสมที่สุดเสมอไป งานวิจัยนี้ยืนยันว่า A* เป็นอัลกอริทึมที่เหมาะสมที่สุดสำหรับการนำทาง NPC ในเกม 2 มิติ ซึ่งสอดคล้องกับการออกแบบระบบ AI ของศัตรูในโครงงานนี้
212 	2.10.7 Improving Mobile Game Performance with Basic Optimization Techniques in Unity
213 		งานวิจัยนี้ศึกษาผลกระทบของเทคนิค Optimization พื้นฐานที่มีต่อประสิทธิภาพของเกมบนอุปกรณ์มือถือ Android โดยพัฒนาเกม Shooter 3 มิติด้วย Unity และ Blender จำนวน 2 เวอร์ชัน ได้แก่ เวอร์ชันที่ใช้เทคนิค Optimization และเวอร์ชันที่ไม่ใช้ โดยเทคนิคที่นำมาทดสอบประกอบด้วย Low Poly Model, Merge Vertices, Textures and Materials, Occlusion Culling และ Object Pooling ตัวชี้วัดประสิทธิภาพที่ใช้คือค่า Frames Per Second (FPS), Batches และจำนวน Triangles/Polygons ซึ่งสะท้อนการใช้งาน CPU, GPU และหน่วยความจำตามลำดับ ผลการทดสอบบนอุปกรณ์มือถือจริงพบว่าเวอร์ชันที่ใช้เทคนิค Optimization รักษาค่า FPS ได้ในช่วง 50–60 FPS ตลอดการเล่น ขณะที่เวอร์ชันที่ไม่ผ่านการ Optimize มีค่า FPS ตกลงเหลือเพียง 20–30 FPS เมื่อมีศัตรูจำนวนมากบนหน้าจอ ทำให้เกมเกิดอาการกระตุก งานวิจัยนี้ยืนยันว่าการเลือกใช้เทคนิค Optimization ที่เหมาะสมมีผลโดยตรงต่อความลื่นไหลของเกม ซึ่งสอดคล้องกับโครงงานนี้ที่ต้องการให้เกม Side-scrolling Horror ทำงานได้อย่างมีประสิทธิภาพบน Unity

220 3.1 การกำหนดปัญหา
221 3.1.1 ปัญหาด้านการควบคุมตัวละครผู้เล่น
222 ตัวละครผู้เล่นต้องรองรับการเดิน การวิ่ง การกระโดด การไต่บันได การซ่อนตัว การใช้ไอเท็ม การได้รับความเสียหาย และการเปลี่ยนฉาก การทำงานเหล่านี้อาจเกิดขึ้นต่อเนื่องหรือขัดแย้งกัน หากไม่มีระบบควบคุมสถานะที่ชัดเจนอาจทำให้ตัวละครรับคำสั่งในช่วงที่ไม่ควรควบคุมได้ โครงงานจึงใช้ FSM กำหนดสถานะ Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ Dead เพื่อควบคุมสิทธิ์การรับคำสั่งและพฤติกรรมในแต่ละช่วง
223 3.1.2 ปัญหาด้านพฤติกรรมของศัตรู
224 ศัตรูต้องตอบสนองต่อผู้เล่นได้หลายลักษณะ ทั้งการลาดตระเวน การหันหาเสียง การตรวจสอบพื้นที่ การค้นหา การไล่ล่า และการโจมตี หากไม่มีลำดับสถานะที่ชัดเจน ศัตรูอาจเปลี่ยนพฤติกรรมอย่างไม่สมเหตุสมผลหรือไม่สามารถกลับไปลาดตระเวนได้หลังจากสูญเสียเป้าหมาย จึงใช้ Enemy FSM ควบคุมลำดับการตัดสินใจจากข้อมูลการมองเห็น การได้ยิน ระดับความสงสัย และตำแหน่งล่าสุดของผู้เล่น
225 3.1.3 ปัญหาด้านระบบตรวจจับ
226 ระบบตรวจจับต้องพิจารณาระยะทาง มุมมอง สิ่งกีดขวาง การเปิดไฟฉาย และเสียงที่เกิดจากกิจกรรมต่าง ๆ ของผู้เล่น การวิ่งมีความสำคัญมากกว่าการเดิน ขณะที่ก้อนหินและกับดักกระจกสร้างเสียงจากตำแหน่งอื่นเพื่อเบี่ยงเบนความสนใจของศัตรู ระบบจึงจำแนกประเภทเสียงเป็น Footstep, Sprint, Rock, Glass และ Environmental ก่อนประเมินความดัง ระยะห่าง และอายุของเสียง
227 3.1.4 ปัญหาด้านตรรกะและเป้าหมายของเกม
228 ผู้เล่นต้องเก็บกุญแจตามจำนวนที่กำหนดก่อนเปิดประตูทางออก ระบบต้องตรวจสอบจำนวนกุญแจ สถานะประตู ระยะการโต้ตอบ และอันตรายรอบตัวผู้เล่น การปลดล็อกต้องกดปุ่มโต้ตอบค้างไว้และยกเลิกได้เมื่อผู้เล่นปล่อยปุ่ม เดินออกจากระยะ ถูกโจมตี หรือมีศัตรูอยู่ใกล้ เพื่อให้เป้าหมายของเกมชัดเจนและมีความท้าทาย
229 3.1.5 ปัญหาด้านส่วนติดต่อผู้ใช้งาน
230 ผู้เล่นต้องรับรู้พลังชีวิต แบตเตอรี่ไฟฉาย พลังงานสำหรับวิ่ง จำนวนก้อนหิน จำนวนกุญแจ ข้อความโต้ตอบ และสถานการณ์อันตรายแบบเรียลไทม์ โดยข้อมูลต้องไม่บดบังพื้นที่เล่น ระบบจึงแสดง HIDDEN เมื่อซ่อนตัว แสดง DANGER เมื่อถูกไล่ล่า และใช้เสียงหัวใจร่วมกับขอบจอสีแดงเมื่อศัตรูอยู่ใกล้
231 3.1.6 ปัญหาด้านการออกแบบและปรับสมดุลด่าน

327 3.5.1 สถาปัตยกรรมของระบบ
328 ระบบประกอบด้วย PlayerController, PlayerHealth, FlashlightController, HidingSystem, FootstepSystem, KillerAI, InventoryManager, ExitDoor, GameManager, UIManager, AudioManager และ TensionDirector โดย PlayerController รับข้อมูลจากผู้เล่นและส่งเหตุการณ์ให้ระบบที่เกี่ยวข้อง FootstepSystem ส่งเหตุการณ์เสียงให้ KillerAI ขณะที่ InventoryManager ส่งจำนวนกุญแจให้ UIManager และ ExitDoor ส่วน GameManager ควบคุมสถานะเกมและการเปลี่ยนฉาก
329 3.5.2 การพัฒนา Player FSM
330 Player FSM ใช้สถานะ Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ Dead เพื่อควบคุมการรับคำสั่ง Normal เป็นสถานะที่อนุญาตการควบคุมทั่วไป Hidden ใช้เมื่ออยู่ในจุดซ่อน Frozen และ Hurt ใช้หยุดหรือจำกัดการควบคุมชั่วคราว UsingItem ป้องกันคำสั่งที่ขัดแย้งระหว่างใช้ไอเท็ม Transitioning ใช้ระหว่างเปลี่ยนฉาก และ Dead ใช้เมื่อพลังชีวิตหมด
331 3.5.3 การพัฒนา Enemy FSM
332 Enemy FSM รับข้อมูลจากระบบการมองเห็นและการได้ยิน จากนั้นประเมินความสงสัยและเลือกสถานะ เสียง Glass และ Sprint มีความสำคัญมากกว่าเสียง Footstep ทั่วไป ศัตรูเก็บตำแหน่งล่าสุดไว้ชั่วคราวเพื่อใช้ตรวจสอบและค้นหา หากไม่พบเป้าหมายจะกลับไปยังเส้นทางลาดตระเวน
333 3.5.4 การพัฒนาระบบความตึงเครียด
334 TensionDirector รวมสถานะของศัตรูทุกตัวเป็น Calm, Suspicious, Hunted, Escaped และ Cooldown ข้อมูลนี้ใช้ควบคุมระดับความตึงเครียด ดนตรีไล่ล่า เสียงหัวใจ ภาพเตือน และตัวคูณความเร็วของศัตรูระหว่างการไล่ล่า
335 3.5.5 การพัฒนาระบบไอเท็มและประตูทางออก

364 เมื่อ isWalking เป็น true ระบบเปลี่ยนจาก Idle ไป Walk และเมื่อเป็น false จะกลับจาก Walk ไป Idle ทั้งสอง Transition ปิด Has Exit Time และมี Transition Duration เท่ากับ 0 จึงเปลี่ยนสถานะได้ทันทีเมื่อเงื่อนไขเป็นจริง โดยไม่ต้องรอให้คลิปเดิมเล่นถึงจุดสิ้นสุด
365 PlayerController ส่งค่าด้วย animator.SetBool(IsWalkingHash, IsMoving) จึงใช้สถานะการเคลื่อนที่ของผู้เล่นเป็นตัวควบคุมภาพจริง ใน Controller ปัจจุบันยังไม่มีสถานะ Run แยกต่างหาก การวิ่งจึงไม่ได้หมายความว่ามีคลิป Run ของผู้เล่นอยู่ในแผนผังนี้
366 Any State เป็นจุดสำหรับกำหนดการเปลี่ยนจากสถานะใดก็ได้ แต่ของผู้เล่นยังไม่มี Transition ออกจากจุดนี้ ส่วน Entry เป็นจุดเริ่มต้น ไม่ใช่คลิปแอนิเมชัน การแยกความหมายของแต่ละกล่องช่วยให้ตีความแผนผังได้ถูกต้อง
367 3.5.9 การพัฒนาระบบแอนิเมชันของ Killer
368 Killer ใช้ KillerAnimator.controller เชื่อมกับ KillerAI เพื่อแสดงท่าทางตามพฤติกรรมของศัตรู ประกอบด้วย Idle สำหรับหยุดนิ่ง Walk สำหรับการเดิน Run สำหรับไล่ล่า Attack1 สำหรับโจมตี และ Scream สำหรับกรีดร้อง ภาพที่ 3-23 จับจากหน้าต่าง Animator ของ Unity โดยจัดตำแหน่งกล่องให้เห็นชื่อสถานะและลูกศรชัดเจน

370 ภาพที่ 3-23 แผนผัง Animator และ Parameters ของ Killer จาก Unity
371 Entry เริ่มที่ Idle ส่วนการเดินใช้ isWalking ชนิด Bool และการวิ่งใช้ isRunning ชนิด Bool สคริปต์กำหนด isWalking เป็น true เมื่ออยู่ใน Patrol, Investigate, InvestigateSound, Search หรือ ReturnToPatrol และมีค่าสัมบูรณ์ของความเร็วแนวนอนมากกว่า 0.01 ส่วน isRunning เป็น true เมื่ออยู่ใน Chase หรือ Attack
372 การโจมตีใช้ attack1 ชนิด Trigger โดย KillerAI เรียก SetTrigger เมื่อโจมตีตามรอบคูลดาวน์ หรือเริ่มตรวจค้นจุดซ่อนที่สงสัย จึงเรียกท่า Attack1 เป็นเหตุการณ์แต่ละครั้ง ขณะที่ scream เป็น Trigger ซึ่งเรียกเมื่อระบบสั่งกรีดร้องหรือใช้ความสามารถหยุดผู้เล่นตามเงื่อนไขของศัตรู
373 Any State เชื่อมไป Scream เพื่อให้การกรีดร้องเริ่มได้จากสถานะใดก็ได้ ส่วน Attack1 รับ Transition จาก Idle, Walk และ Run จึงไม่ได้ใช้ Any State สำหรับการโจมตี เมื่อ Attack1 หรือ Scream เล่นครบตาม Exit Time เท่ากับ 1 จะกลับ Idle แล้วตรวจพารามิเตอร์การเคลื่อนที่เพื่อเลือกสถานะถัดไป
374 3.5.10 เงื่อนไขการเปลี่ยนแอนิเมชันและการเชื่อมกับ FSM
375 ลูกศรในภาพที่ 3-23 แสดงทิศทางที่ Animator เปลี่ยนสถานะได้ เงื่อนไขของ Transition ต้องสอดคล้องกับค่าที่ KillerAI ส่งเข้ามา โดย Controller ปัจจุบันกำหนดเส้นทางดังต่อไปนี้
376 Idle ไป Walk เมื่อ isWalking เป็น true และ Walk กลับ Idle เมื่อ isWalking เป็น false
377 Idle หรือ Walk ไป Run เมื่อ isRunning เป็น true และ Run กลับ Idle เมื่อ isRunning เป็น false
378 Run ไป Walk เมื่อ isRunning เป็น false และ isWalking เป็น true โดยเงื่อนไขทั้งสองต้องเป็นจริงร่วมกัน
379 Idle, Walk หรือ Run ไป Attack1 เมื่อได้รับ Trigger attack1 และ Attack1 กลับ Idle ด้วย Has Exit Time ที่ค่า 1
380 Any State ไป Scream เมื่อได้รับ Trigger scream และ Scream กลับ Idle ด้วย Has Exit Time ที่ค่า 1
381 Transition ระหว่างการเคลื่อนที่ของ Killer มี Duration เท่ากับ 0.1 วินาที และปิด Has Exit Time เพื่อให้ตอบสนองต่อพฤติกรรมได้โดยไม่รอจบรอบคลิป การเข้าสู่ Attack1 ใช้ Duration 0.05 วินาที ส่วน Any State ไป Scream ใช้ Duration 0 เพื่อเริ่มกรีดร้องทันที การกลับจาก Attack1 และ Scream ใช้ Duration 0.1 วินาที
382 FSM ใน KillerAI รับหน้าที่ตัดสินใจ เช่น ลาดตระเวน ค้นหา ไล่ล่า หรือโจมตี ส่วน Animator รับหน้าที่แสดงภาพของการตัดสินใจนั้น จึงไม่จำเป็นต้องมีจำนวนสถานะเท่ากัน ตัวอย่างเช่น Patrol และ Search ใช้ภาพ Walk ร่วมกันได้ แต่ยังมีตรรกะเลือกเป้าหมายต่างกันใน FSM
383 สำหรับผู้เล่น หลักการเดียวกันใช้กับ Player FSM ซึ่งควบคุมการรับคำสั่งและข้อจำกัดในสถานะ Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ Dead ส่วน PlayerAnimator ปัจจุบันเลือกภาพระหว่าง Idle กับ Walk ตาม IsMoving การเพิ่มสถานะใน FSM จึงไม่ทำให้เกิดคลิปแอนิเมชันใหม่โดยอัตโนมัติ
384 การคำนวณความเสียหายอยู่ใน KillerAI ซึ่งเรียก playerHealth.TakeDamage ก่อนส่ง Trigger attack1 แอนิเมชันโจมตีจึงเป็นภาพประกอบเหตุการณ์ ไม่ใช่ตัวกำหนดความเสียหายด้วย Animation Event ในส่วนโค้ดนี้ หากต้องการให้ความเสียหายตรงกับเฟรมที่อาวุธสัมผัสผู้เล่น จึงค่อยออกแบบ Animation Event เพิ่มเติม
385 เมื่อ isRunning เป็น false และ isWalking เป็น true เส้นจาก Run ไป Idle กับเส้นไป Walk อาจผ่านเงื่อนไขพร้อมกัน จึงควรตรวจลำดับ Transition เพื่อให้ผลการเปลี่ยนภาพสอดคล้องกับพฤติกรรมที่ต้องการ
386 3.5.11 เหตุผลในการเลือกชนิดพารามิเตอร์ของ Animator
387 Unity มีพารามิเตอร์ Float, Int, Bool และ Trigger เพื่อแทนข้อมูลต่างลักษณะ การเลือกชนิดขึ้นอยู่กับว่าเป็นค่าต่อเนื่อง รหัสสถานะ เงื่อนไขที่คงอยู่ หรือเหตุการณ์เฉพาะครั้ง ไม่จำเป็นต้องใช้ครบทั้งสี่ชนิดใน Controller เดียว โครงการนี้ใช้ Bool และ Trigger จริง ส่วน Float และ Int อธิบายเป็นทางเลือกสำหรับการขยายระบบ
388 Float สำหรับค่าต่อเนื่อง
389 Float เก็บตัวเลขที่มีทศนิยม เหมาะกับค่าความเร็ว เช่น 0, 1.5 และ 3.2 หากเพิ่มพารามิเตอร์ Speed จะส่งค่าด้วย SetFloat และใช้เปรียบเทียบกับเกณฑ์หรือควบคุม Blend Tree เพื่อผสมท่ายืน เดิน และวิ่งตามความเร็วได้ เหตุผลที่เลือก Float คือรักษารายละเอียดระหว่างค่าความเร็วซึ่ง Int จะเก็บไม่ได้ ปัจจุบันยังไม่มีพารามิเตอร์ Float ใน Animator ทั้งสองตัว
390 Int สำหรับรหัสหรือทางเลือกหลายค่า
391 Int เก็บจำนวนเต็ม เหมาะกับการแทนโหมดที่แยกกัน เช่น MovementMode เท่ากับ 0 สำหรับยืน 1 สำหรับเดิน และ 2 สำหรับวิ่ง แล้วส่งค่าด้วย SetInteger เหตุผลที่เลือก Int คือใช้ค่าเดียวระบุทางเลือกหลายแบบ ลดการใช้ Bool หลายตัวที่อาจเป็น true พร้อมกัน อย่างไรก็ตาม ตัวแปร int ที่เก็บผล Animator.StringToHash เป็นเพียงรหัสอ้างอิงชื่อพารามิเตอร์ ไม่ได้ทำให้พารามิเตอร์นั้นเป็นชนิด Int และ Controller ปัจจุบันยังไม่ได้ใช้ Int
392 Bool สำหรับเงื่อนไขที่ต้องคงสถานะ
393 Bool มีค่า true หรือ false เหมาะกับคำถามว่ากำลังเดินหรือกำลังวิ่งหรือไม่ จึงใช้ isWalking ในผู้เล่น และ isWalking กับ isRunning ใน Killer โดยส่งค่าด้วย SetBool เหตุผลที่เลือก Bool คือระบบต้องรักษาค่าขณะพฤติกรรมยังดำเนินอยู่ และเปลี่ยนกลับเมื่อพฤติกรรมหยุด ทำให้การเข้าและออกจาก Walk หรือ Run ตรวจสอบได้ตรงไปตรงมา
394 Trigger สำหรับเหตุการณ์เฉพาะครั้ง
395 Trigger เหมาะกับคำสั่งเริ่มการกระทำ เช่น โจมตีหรือกรีดร้อง จึงใช้ attack1 และ scream ผ่าน SetTrigger เมื่อ Transition ใช้ Trigger แล้ว Controller จะรีเซ็ตค่าโดยอัตโนมัติ หากยังไม่มี Transition ใช้ค่านั้น อาจต้องเรียก ResetTrigger เพื่อยกเลิกคำสั่งที่ค้างอยู่ เหตุผลที่เลือก Trigger คือไม่ต้องเปิด Bool ค้างไว้และคอยสั่งปิดเองทุกครั้ง ส่วนการออกจากคลิปยังต้องกำหนด Transition และ Exit Time ให้เหมาะสม
396 แหล่งตรวจสอบระบบคือ PlayerAnimator.controller, KillerAnimator.controller, PlayerController.cs และ KillerAI.cs ในโปรเจกต์ SideScrollingEscape ส่วนชนิดพารามิเตอร์อ้างอิง Unity Manual เรื่อง Animation Parameters ที่ https://docs.unity3d.com/6000.4/Documentation/Manual/AnimationParameters.html ตรวจสอบวันที่ 4 ตุลาคม 2569

452 ระบบปัญญาประดิษฐ์ของศัตรูได้รับการพัฒนาให้ตอบสนองต่อผู้เล่นผ่านการมองเห็นและการได้ยิน โดยมี KillerAI เป็นส่วนควบคุมพฤติกรรมหลัก ศัตรูสามารถลาดตระเวน รับรู้สิ่งผิดปกติ ตรวจสอบตำแหน่งเสียง ค้นหาผู้เล่น ไล่ล่า โจมตี และกลับไปยังเส้นทางลาดตระเวนได้ Enemy FSM ประกอบด้วยสถานะ Patrol, Alert, Listening, InvestigateSound, ConfirmSound, Confused, Investigate, Search, Chase, Attack, AttackRecover, ReturnToPatrol และ Scream สถานะเหล่านี้ทำให้ศัตรูสามารถตอบสนองต่อสถานการณ์ได้ละเอียดกว่าการแบ่งพฤติกรรมเพียงการลาดตระเวนและไล่ล่า ในสถานะ Patrol ศัตรูจะเดินตามเส้นทางลาดตระเวน เมื่อได้ยินเสียงจะเข้าสู่กระบวนการ Listening และ InvestigateSound เพื่อเลือกและเดินทางไปยังตำแหน่งกำเนิดเสียง หากตรวจสอบแล้วยังไม่พบผู้เล่น ศัตรูอาจเข้าสู่สถานะ Confused, Investigate หรือ Search ก่อนกลับไปลาดตระเวน เมื่อศัตรูตรวจพบผู้เล่น ระบบจะเปลี่ยนเข้าสู่สถานะ Chase และเคลื่อนที่ไล่ตามตำแหน่งของผู้เล่น หากผู้เล่นอยู่ในระยะโจมตี ศัตรูจะเข้าสู่สถานะ Attack หลังจากโจมตีแล้วจะพักตามระยะเวลาที่กำหนดในสถานะ AttackRecover ก่อนตัดสินใจไล่ตามหรือตรวจสอบพื้นที่ต่อไป

580 ผลการดำเนินโครงงานสามารถสรุปตามวัตถุประสงค์ได้ดังนี้
581 5.1.1 ผลการพัฒนาระบบควบคุมตัวละครผู้เล่น
582 สามารถพัฒนาระบบควบคุมตัวละครผู้เล่นให้รองรับการเดิน วิ่ง กระโดด ใช้ไฟฉาย เก็บไอเท็ม ซ่อนตัว เปิดกระเป๋าไอเท็ม และโต้ตอบกับประตูทางออกได้ การวิ่งส่งผลให้ผู้เล่นเคลื่อนที่เร็วขึ้น แต่ทำให้ Stamina ลดลงและสร้างเสียงที่ศัตรูสามารถตรวจจับได้ ส่วนไฟฉายมีปริมาณแบตเตอรี่จำกัด ทำให้ผู้เล่นต้องวางแผนการใช้งานระหว่างสำรวจด่าน
583 ระบบควบคุมผู้เล่นใช้ FSM แบ่งสถานะออกเป็น Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ Dead การแบ่งสถานะดังกล่าวช่วยควบคุมเงื่อนไขการรับคำสั่งและป้องกันพฤติกรรมที่ขัดแย้งกัน เช่น การควบคุมตัวละครระหว่างเสียชีวิต การเคลื่อนที่ขณะถูกหยุด หรือการรับคำสั่งระหว่างเปลี่ยนฉาก
584 5.1.2 ผลการพัฒนาระบบปัญญาประดิษฐ์ของศัตรู
585 สามารถพัฒนาระบบปัญญาประดิษฐ์ของศัตรูให้ตอบสนองต่อผู้เล่นผ่านการมองเห็นและการได้ยิน ศัตรูสามารถลาดตระเวน รับฟังเสียง ตรวจสอบตำแหน่งที่เกิดเสียง ค้นหาผู้เล่น ไล่ล่า โจมตี และกลับไปยังเส้นทางลาดตระเวนได้ Enemy FSM ประกอบด้วยสถานะ Patrol, Alert, Listening, InvestigateSound, ConfirmSound, Confused, Investigate, Search, Chase, Attack, AttackRecover, ReturnToPatrol และ Scream สถานะเหล่านี้ช่วยให้ศัตรูมีพฤติกรรมหลายขั้นตอนและตอบสนองต่อสถานการณ์ได้เหมาะสมกว่าการกำหนดเงื่อนไขทั้งหมดไว้ในกระบวนการเดียว
586 เมื่อศัตรูได้ยินเสียงจากการเดิน วิ่ง หรือกับดัก ศัตรูจะจดจำตำแหน่งกำเนิดเสียงไว้ชั่วคราวและเคลื่อนที่ไปตรวจสอบ หากมองเห็นผู้เล่นจะเปลี่ยนเข้าสู่สถานะ Chase และโจมตีเมื่อผู้เล่นอยู่ในระยะที่กำหนด หากสูญเสียการตรวจจับ ศัตรูจะตรวจสอบตำแหน่งล่าสุดหรือค้นหาในบริเวณใกล้เคียงก่อนกลับไปลาดตระเวน
587 5.1.3 ผลการพัฒนาระบบตรวจจับ
588 สามารถพัฒนาระบบตรวจจับด้วยการมองเห็นและการได้ยินให้ทำงานร่วมกับ Enemy FSM ได้ ระบบการมองเห็นพิจารณาระยะตรวจจับ ทิศทาง และสิ่งกีดขวางภายในฉาก ส่วนระบบการได้ยินรับเหตุการณ์เสียงจากการกระทำของผู้เล่นและวัตถุภายในด่าน
589 เสียงแต่ละประเภทมีความสำคัญแตกต่างกัน โดยเสียงจากการวิ่งและเสียงจากกับดักกระจกสามารถดึงดูดความสนใจของศัตรูได้มากกว่าเสียงเดินทั่วไป ระบบดังกล่าวทำให้เสียงเป็นส่วนหนึ่งของการเล่น ผู้เล่นจึงต้องเลือกระหว่างการเคลื่อนที่อย่างรวดเร็วกับการลดโอกาสที่ศัตรูจะตรวจพบตำแหน่ง
590 5.1.4 ผลการพัฒนาระบบไอเท็มและประตูทางออก
591 สามารถพัฒนาระบบเก็บกุญแจและกระเป๋าไอเท็มโดยใช้ InventoryManager สำหรับจัดเก็บและตรวจสอบจำนวนไอเท็ม เมื่อผู้เล่นเก็บกุญแจ ข้อมูลบน HUD และในกระเป๋าไอเท็มจะได้รับการปรับปรุงตามจำนวนที่เก็บได้
592 ระบบประตูทางออกใช้ FSM แบ่งสถานะเป็น Locked, Ready, Unlocking, Open, Transitioning และ Completed ประตูจะยังไม่สามารถเปิดได้หากผู้เล่นเก็บกุญแจไม่ครบ เมื่อผู้เล่นมีจำนวนกุญแจตามที่กำหนดและกดปุ่มโต้ตอบค้าง ระบบจะแสดงความคืบหน้าการปลดล็อก ก่อนเปิดประตูและเปลี่ยนไปยังด่านถัดไปหรือแสดงผลการจบเกม
593 5.1.5 ผลการพัฒนาด่านและบรรยากาศของเกม
594 สามารถพัฒนาด่านภายในเกมให้มีระดับความยากแตกต่างกันผ่าน LevelConfig ซึ่งกำหนดค่าต่าง ๆ เช่น ความเร็วของศัตรู ระยะการมองเห็น ระยะการได้ยิน ความเสียหาย และปริมาณแบตเตอรี่เริ่มต้น
595 Level 3 ได้รับการออกแบบให้เป็นสวนสนุก โดยต้นไม้ พุ่มไม้ พื้นหญ้า และเส้นทางต่างระดับเพื่อสร้างบรรยากาศน่ากลัว ภายในด่านมีการสุ่มตำแหน่งกุญแจและกับดักในพื้นที่ที่ผู้เล่นสามารถเดินถึง ทำให้การเล่นแต่ละรอบมีความแตกต่างกัน
596 ศัตรูใน Level 3 เน้นการตรวจจับด้วยเสียง มีความเร็วในการไล่ล่าและระยะการได้ยินสูงกว่าด่านอื่น เมื่อผู้เล่นเข้าใกล้ศัตรูหรือถูกไล่ล่า ระบบจะเล่นเสียงหัวใจ แสดงขอบจอเตือน และปรับระดับดนตรีตามสถานการณ์ ส่งผลให้ผู้เล่นรับรู้ถึงอันตรายและความกดดันได้อย่างชัดเจน

599 5.1.6 ผลการพัฒนาส่วนติดต่อผู้ใช้งาน
600 สามารถพัฒนาส่วนติดต่อผู้ใช้งานให้แสดงข้อมูลสำคัญระหว่างเล่น ได้แก่ พลังชีวิต Stamina ปริมาณแบตเตอรี่ จำนวนกุญแจ ข้อความโต้ตอบ สถานะการซ่อน และคำเตือนเมื่อศัตรูอยู่ใกล้
601 ระบบแสดงผลจะเปลี่ยนตามสถานการณ์ เช่น แสดงข้อความแนะนำเมื่อผู้เล่นเข้าใกล้วัตถุ แสดง DANGER เมื่อศัตรูไล่ล่า แสดง Game Over เมื่อผู้เล่นเสียชีวิต และแสดง Level Complete หรือ Game Won เมื่อผู้เล่นผ่านเงื่อนไขของด่าน
602 5.1.7 อภิปรายผลการพัฒนา
603 ผลการพัฒนาแสดงให้เห็นว่า Finite State Machine เหมาะสำหรับระบบที่ประกอบด้วยพฤติกรรมหลายสถานะและมีเงื่อนไขการเปลี่ยนสถานะที่ชัดเจน เนื่องจากช่วยแยกหน้าที่ของแต่ละสถานะ ลดความซับซ้อนของการตรวจสอบเงื่อนไข และช่วยให้สามารถติดตามพฤติกรรมของระบบได้ง่ายขึ้น
604 ผลดังกล่าวสอดคล้องกับหลักการของ FSM ที่กำหนดให้ระบบอยู่ในสถานะหนึ่ง ณ ช่วงเวลาหนึ่ง และเปลี่ยนไปยังสถานะใหม่เมื่อเกิดเหตุการณ์หรือเป็นไปตามเงื่อนไขที่กำหนด การนำแนวคิดนี้มาใช้กับผู้เล่นช่วยป้องกันคำสั่งที่ขัดแย้งกัน ส่วนการใช้กับศัตรูช่วยให้กระบวนการลาดตระเวน ตรวจจับ ค้นหา ไล่ล่า และโจมตีมีลำดับที่ชัดเจน
605 การใช้ระบบตรวจจับด้วยเสียงร่วมกับ FSM ช่วยเพิ่มความหลากหลายของพฤติกรรมศัตรู เนื่องจากศัตรูไม่จำเป็นต้องมองเห็นผู้เล่นโดยตรงจึงจะตอบสนองได้ อย่างไรก็ตาม ความสมจริงของศัตรูยังขึ้นอยู่กับการกำหนดค่าความเร็ว ระยะตรวจจับ ระยะเวลาของแต่ละสถานะ และรูปแบบพื้นที่ภายในด่าน หากกำหนดค่าไม่เหมาะสม เกมอาจง่ายหรือยากเกินไป
606 การแบ่งระบบออกเป็นส่วนย่อย เช่น PlayerController, KillerAI, InventoryManager, ExitDoor, GameManager, UIManager และ TensionDirector ช่วยให้สามารถปรับปรุงแต่ละระบบได้โดยไม่กระทบส่วนอื่นมากเกินไป และช่วยให้ตรวจสอบข้อผิดพลาดได้สะดวกกว่าการรวมการทำงานทั้งหมดไว้ในสคริปต์เดียว
607 5.2 ปัญหาที่พบในโครงงาน
608 5.2.1 ปัญหาการเปลี่ยนสถานะของ FSM
609 ในระหว่างการพัฒนา พบว่าบางสถานการณ์ทำให้ระบบพยายามเปลี่ยนสถานะมากกว่าหนึ่งครั้งในเวลาใกล้เคียงกัน เช่น ผู้เล่นได้รับความเสียหายขณะเปิดกระเป๋า ถูกศัตรูโจมตีระหว่างปลดล็อกประตู หรือศัตรูได้ยินเสียงพร้อมกับมองเห็นผู้เล่น ปัญหานี้อาจทำให้คำสั่งบางอย่างทำงานซ้อนกันหรือระบบเปลี่ยนไปยังสถานะที่ไม่เหมาะสม
610 แนวทางแก้ไขคือกำหนดลำดับความสำคัญของสถานะ ตรวจสอบสถานะปัจจุบันก่อนรับคำสั่ง และจำกัดให้แต่ละระบบเปลี่ยนสถานะผ่านฟังก์ชันส่วนกลาง เช่น SetPlayerState() หรือ SetState() เพื่อให้สามารถควบคุมการเปลี่ยนสถานะได้จากตำแหน่งเดียว
611 
612 5.2.2 ปัญหาการตรวจจับของศัตรู
613 ระบบการมองเห็นของศัตรูอาจตรวจจับผิดพลาดเมื่อผู้เล่นอยู่ใกล้ขอบสิ่งกีดขวาง หรือเมื่อ Collider ของวัตถุไม่ตรงกับภาพที่แสดงในฉาก ส่วนระบบการได้ยินอาจทำให้ศัตรูตอบสนองต่อเสียงหลายเหตุการณ์พร้อมกัน จนเกิดการเปลี่ยนเป้าหมายบ่อยเกินไป
614 แนวทางแก้ไขคือปรับ LayerMask และ Collider ให้ตรงกับวัตถุ ตรวจสอบแนว Raycast ที่ใช้ในการมองเห็น และกำหนดระดับความสำคัญของเสียง ศัตรูจะเลือกตรวจสอบเสียงที่มีความสำคัญมากกว่าหรือเสียงที่เกิดขึ้นล่าสุด พร้อมเก็บตำแหน่งเสียงไว้เพียงช่วงเวลาที่กำหนด
615 5.2.3 ปัญหาการเคลื่อนที่ของศัตรูในฉากสองมิติ
616 ศัตรูอาจติดขอบพื้น สิ่งกีดขวาง หรือพื้นที่ต่างระดับ โดยเฉพาะฉากที่ประกอบจาก Tilemap หลายชั้น หากจุดลาดตระเวนอยู่ในตำแหน่งที่ศัตรูเดินไม่ถึง ระบบอาจพยายามเคลื่อนที่ไปยังเป้าหมายเดิมอย่างต่อเนื่อง
617 แนวทางแก้ไขคือกำหนดเส้นทางลาดตระเวนให้สอดคล้องกับพื้นที่ที่เดินได้ ตรวจสอบพื้นและขอบทางเดินก่อนเปลี่ยนทิศทาง รวมถึงกำหนดเงื่อนไขให้ศัตรูกลับไปยังจุดลาดตระเวนที่เหมาะสมเมื่อไม่สามารถเดินทางไปยังเป้าหมายเดิมได้
618 5.2.4 ปัญหาการสุ่มตำแหน่งวัตถุใน Level 3
619 การสุ่มตำแหน่งกุญแจและกับดักอาจทำให้วัตถุปรากฏซ้อนกัน อยู่ใกล้กันเกินไป หรืออยู่ในตำแหน่งที่ผู้เล่นไม่สามารถเข้าถึงได้ หากสุ่มโดยใช้พิกัดทั่วไปโดยไม่ตรวจสอบพื้นภายในฉาก
620 แนวทางแก้ไขคือให้ Level3RandomEvents เลือกตำแหน่งจากพื้นที่ที่ตรวจสอบแล้วว่าสามารถเดินได้ กำหนดระยะห่างขั้นต่ำระหว่างวัตถุ และแยกจุดสุ่มของกุญแจกับกับดัก เพื่อลดโอกาสที่วัตถุหลายชิ้นจะรวมอยู่ในบริเวณเดียวกัน
621 5.2.5 ปัญหาการปรับสมดุลระดับความยาก
622 ค่าความเร็ว ระยะการมองเห็น ระยะการได้ยิน และความเสียหายของศัตรูมีผลต่อความยากอย่างมาก หากเพิ่มหลายค่าพร้อมกัน ผู้เล่นอาจไม่มีเวลาเพียงพอสำหรับหลบหนีหรือหาจุดซ่อน โดยเฉพาะ Level 3 ซึ่งกำหนดให้ศัตรูมีความเร็วและระยะการได้ยินสูง
623 แนวทางแก้ไขคือแยกค่าความยากของแต่ละด่านไว้ใน LevelConfig และปรับค่าทีละส่วนจากผลการทดลองเล่น เช่น ปรับความเร็วไล่ล่า ระยะได้ยิน เวลาค้นหา และจำนวนจุดซ่อน เพื่อหาค่าที่สร้างความกดดันโดยยังเปิดโอกาสให้ผู้เล่นสามารถผ่านด่านได้
624 5.2.6 ปัญหาการจัดวางกล้องและองค์ประกอบของด่าน
625 กล้องอาจอยู่ต่ำหรือสูงเกินไป ทำให้ไม่สามารถมองเห็นเส้นทางและองค์ประกอบสำคัญของด่านได้ครบถ้วน นอกจากนี้ การใช้ขอบเขตกล้องร่วมกันกับด่านที่มีขนาดแตกต่างกันอาจทำให้เกิดพื้นที่ว่างนอกฉากหรือทำให้วัตถุบางส่วนอยู่นอกหน้าจอ
626 แนวทางแก้ไขคือกำหนดตำแหน่งและขอบเขตกล้องแยกตามแต่ละด่าน ปรับค่าแกนตั้งของกล้องให้เหมาะกับระดับพื้น และทดสอบบริเวณขอบซ้าย ขอบขวา พื้นที่ชั้นบน และพื้นที่ชั้นล่างก่อนสรุปการจัดวางด่าน
627 5.2.7 ปัญหาการทำงานร่วมกันของหลายระบบ
628 ระบบผู้เล่น ศัตรู UI เสียง ไอเท็ม และการเปลี่ยนฉากมีการส่งข้อมูลถึงกันหลายส่วน หากวัตถุหรือคอมโพเนนต์บางรายการไม่ได้กำหนดใน Inspector อาจเกิดข้อผิดพลาดหรือทำให้ฟังก์ชันบางอย่างไม่ทำงาน
629 แนวทางแก้ไขคือเพิ่มการตรวจสอบค่าว่างก่อนเรียกใช้งาน แยกความรับผิดชอบของแต่ละสคริปต์ ใช้ Event สำหรับส่งข้อมูลระหว่างระบบที่ไม่จำเป็นต้องอ้างอิงกันโดยตรง และตรวจสอบ Unity Console ทุกครั้งหลังแก้ไข Scene, Prefab หรือสคริปต์ส่วนกลาง
630 5.2.8 สิ่งที่ได้เรียนรู้จากการพัฒนา
631 ผู้พัฒนาได้เรียนรู้ว่าการออกแบบโครงสร้างระบบก่อนเขียนโปรแกรมช่วยลดการแก้ไขโค้ดในภายหลัง การแบ่งระบบออกเป็นโมดูลและกำหนดสถานะด้วย FSM ทำให้สามารถวิเคราะห์สาเหตุของข้อผิดพลาดได้ชัดเจนขึ้น
632 นอกจากนี้ การทดสอบจากการเล่นจริงมีความสำคัญต่อการพัฒนาเกม เนื่องจากระบบที่ทำงานถูกต้องตามโค้ดอาจยังไม่ให้ประสบการณ์ที่เหมาะสม เช่น ศัตรูอาจเร็วเกินไป คำเตือนอาจไม่ชัดเจน หรือการจัดวางวัตถุอาจทำให้ผู้เล่นไม่เข้าใจเส้นทาง ดังนั้นผลจากผู้ทดลองเล่นจึงควรถูกนำมาใช้ร่วมกับการทดสอบทางเทคนิค
633 5.3 ข้อเสนอแนะ
634 5.3.1 ข้อเสนอแนะสำหรับการนำระบบไปใช้
635 ก่อนนำเกมไปใช้งานหรือเผยแพร่ ควรทดสอบกรณีทดสอบทั้งหมดและบันทึกผลที่เกิดขึ้นจริง โดยเฉพาะการเปลี่ยนสถานะของผู้เล่นและศัตรู การตรวจจับเสียง การปลดล็อกประตู และการผ่าน Level 3 ไม่ควรสรุปว่าระบบสมบูรณ์จากการตรวจสอบโค้ดเพียงอย่างเดียว
636 ควรทดสอบกับอุปกรณ์ที่มีประสิทธิภาพแตกต่างกัน ตรวจสอบอัตราเฟรม ความละเอียดหน้าจอ ตำแหน่ง UI และการตอบสนองของปุ่มควบคุม เนื่องจากผลการทำงานอาจแตกต่างกันตามขนาดหน้าจอและความสามารถของอุปกรณ์
637 การปรับค่าความยากผ่าน LevelConfig ควรดำเนินการอย่างระมัดระวัง เพราะความเร็ว ระยะตรวจจับ ความเสียหาย และทรัพยากรเริ่มต้นมีผลต่อกัน หากต้องการปรับความยากควรเปลี่ยนค่าทีละส่วนและทดลองเล่นซ้ำก่อนนำไปใช้จริง
638 5.3.2 ข้อเสนอแนะสำหรับการพัฒนาระบบเพิ่มเติม
639 ควรเพิ่มรูปแบบพฤติกรรมของศัตรูให้หลากหลาย เช่น การตรวจสอบจุดซ่อน การคาดเดาเส้นทางของผู้เล่น การตอบสนองร่วมกันของศัตรูหลายตัว และการจดจำพื้นที่ที่พบผู้เล่นบ่อย เพื่อให้การเล่นแต่ละรอบไม่สามารถคาดเดาได้ง่าย
640 ควรเพิ่มความหลากหลายของไอเท็ม เช่น ไอเท็มฟื้นฟูพลังชีวิต แบตเตอรี่สำรอง อุปกรณ์สร้างเสียงล่อศัตรู หรือไอเท็มป้องกันการโจมตีชั่วคราว โดยต้องกำหนดข้อจำกัดเพื่อไม่ให้ไอเท็มลดความน่ากลัวของเกมมากเกินไป
641 ควรพัฒนาระบบตั้งค่าให้รองรับการปรับระดับเสียง ความสว่าง ความละเอียดหน้าจอ และการกำหนดปุ่มควบคุมใหม่ รวมถึงเพิ่มตัวเลือกด้านการเข้าถึง เช่น ขนาดข้อความ คำบรรยายเสียง และการปรับความรุนแรงของเอฟเฟกต์ภาพ
642 ควรเพิ่มระบบบันทึกความคืบหน้าในอนาคต โดยต้องกำหนดข้อมูลที่จำเป็น เช่น ด่านปัจจุบัน จำนวนไอเท็ม สถานะผู้เล่น และค่าตั้งค่า พร้อมตรวจสอบความถูกต้องของข้อมูลก่อนโหลดกลับเข้าสู่เกม
643 5.3.3 ข้อเสนอแนะสำหรับการศึกษาและวิจัยครั้งต่อไป
644 การศึกษาครั้งต่อไปควรเปรียบเทียบประสิทธิภาพของ FSM กับเทคนิคควบคุมพฤติกรรมแบบอื่น เช่น Behavior Tree หรือ Utility AI โดยพิจารณาความซับซ้อนของโค้ด เวลาในการประมวลผล ความสะดวกในการเพิ่มพฤติกรรม และความสมจริงที่ผู้เล่นรับรู้
645 ควรศึกษาผลของเสียงต่อพฤติกรรมของผู้เล่น โดยทดลองปรับระดับความดัง ความถี่ของเสียงหัวใจ และระยะการได้ยินของศัตรู แล้วประเมินว่าค่าใดสามารถสร้างความกดดันได้เหมาะสมโดยไม่ทำให้ผู้เล่นสับสนหรือรู้สึกว่าเกมไม่ยุติธรรม
646 ควรศึกษาการสุ่มตำแหน่งวัตถุและเหตุการณ์ภายในด่านว่ามีผลต่อความน่ากลัวและความต้องการเล่นซ้ำหรือไม่ โดยเปรียบเทียบระหว่างด่านที่มีตำแหน่งคงที่กับด่านที่มีการสุ่ม พร้อมเก็บข้อมูลระยะเวลาเล่น จำนวนครั้งที่ถูกจับ และความคิดเห็นของผู้เล่น
647 นอกจากนี้ ควรเพิ่มจำนวนผู้ทดลองเล่นและคัดเลือกกลุ่มที่มีประสบการณ์เล่นเกมแตกต่างกัน เพื่อให้ผลการประเมินครอบคลุมทั้งผู้เล่นใหม่และผู้ที่คุ้นเคยกับเกมแนวสยองขวัญ ข้อมูลที่ได้จะช่วยให้สามารถปรับระดับความยาก การควบคุม และการนำเสนอข้อมูลบนหน้าจอได้เหมาะสมมากขึ้น
