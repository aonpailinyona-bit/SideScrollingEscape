บทคัดย่อ
โครงงานนี้มีวัตถุประสงค์เพื่อพัฒนาเกมสองมิติแนวเอาชีวิตรอดและลอบเร้นด้วย Unity 
และภาษา C# โดยใช้เครื่องสถานะจำกัด (Finite State Machine: FSM) ควบคุมตัวละครผู้เล่นและศัตรู 
Killer ระบบผู้เล่นประกอบด้วย Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ 
Dead ส่วนศัตรูใช้สถานะสำหรับลาดตระเวน รับรู้เสียง ตรวจสอบ ค้นหา ไล่ล่า โจมตี และกรีดร้อง 
การตรวจจับใช้ Raycasting ร่วมกับเหตุการณ์เสียง 
ผู้เล่นต้องเก็บกุญแจให้ครบและปลดล็อกประตูเพื่อผ่านด่านทั้งสาม ระบบ Animator 
เชื่อมพฤติกรรมกับภาพเคลื่อนไหวผ่านพารามิเตอร์ Bool และ Trigger ผลจากการตรวจโค้ดและสาธิตใน 
Play Mode พบโครงสร้างระบบและหน้าจอแสดงผลตามสถานะที่กำหนด อย่างไรก็ตาม 
การสาธิตมีการควบคุมตำแหน่งและเรียกสถานะผ่านสคริปต์ 
จึงยังไม่ยืนยันการเล่นครบวงจรหรือความถูกต้องทุกกรณี 
ยังไม่ได้เก็บแบบสอบถามจากผู้ทดลองเล่นและไม่สามารถสรุประดับความพึงพอใจจริงได้ 
รายงานแสดงแผนทดสอบ ข้อจำกัด 
และตัวอย่างข้อมูลสมมติสำหรับอธิบายวิธีวิเคราะห์คะแนนโดยแยกจากผลจริงอย่างชัดเจน

โครงงานวิจัยฉบับนี้สำเร็จลุล่วงไปได้ด้วยดีเนื่องด้วยความกรุณาจาก อาจารย์ธนวัฒน์ ถาวรกูล 
และ ผศ.วราภรณ์ มั่นทุ่ง อาจารย์ที่ปรึกษาโครงงาน ที่ได้ให้คำปรึกษา แนะนำแนวทาง 
และแก้ไขข้อบกพร่องต่าง ๆ ในการพัฒนาเกมสยองขวัญ 2 มิติด้วยภาษา C# 
ตลอดจนถ่ายทอดความรู้และเทคนิคต่าง ๆ ในการใช้โปรแกรม Unity จนโครงงานเล่มนี้เสร็จสมบูรณ์
ขอกราบขอบพระคุณบิดา มารดา และครอบครัว ที่สนับสนุนการศึกษาและการจัดทำโครงงาน 
รวมถึงผู้ที่ให้คำแนะนำและความช่วยเหลือในการพัฒนาระบบ 
ทั้งนี้การเก็บข้อมูลประเมินความพึงพอใจจากผู้ทดลองเล่นยังเป็นขั้นตอนที่จะดำเนินการต่อไป
คุณค่าและประโยชน์ของโครงงานวิจัยฉบับนี้ ผู้จัดทำขอมอบเป็นเครื่องบูชาพระคุณบิดา มารดา 
ครูบาอาจารย์ และผู้มีพระคุณทุกท่านที่มีส่วนช่วยให้ผู้จัดทำประสบความสำเร็จในการศึกษา

1.1 ความเป็นมาและความสำคัญของปัญหา
เกมแนวลอบเร้นต้องควบคุมการเคลื่อนที่ การซ่อนตัว การใช้ไอเท็ม 
และการตอบสนองต่ออันตรายให้สัมพันธ์กัน หากตรวจเงื่อนไขทั้งหมดโดยไม่มีโครงสร้างสถานะ 
อาจเกิดคำสั่งที่ขัดแย้ง เช่น การเคลื่อนที่ขณะซ่อนหรือเสียชีวิต โครงงานจึงใช้ FSM 
แยกพฤติกรรมและเงื่อนไขการรับคำสั่งของผู้เล่นและศัตรูให้ตรวจสอบได้ชัดเจน
นอกจากนี้ การสร้างศัตรูคอมพิวเตอร์ (AI Agent) ให้มีความฉลาดและตอบสนองต่อพฤติกรรม
ของผู้เล่นอย่างสมจริง จำเป็นต้องประยุกต์ใช้อัลกอริทึมขั้นสูง เช่น Finite State Machine (FSM) ในการ
จำแนกสถานะ และการคำนวณทางคณิตศาสตร์เวกเตอร์ (Vector Mathematics) เพื่อตรวจสอบการ
มองเห็น (Line of Sight) และการได้ยินเสียงที่แปรผันตามท่าทางของผู้เล่น
ผู้จัดทำจึงมีแนวคิดพัฒนาโครงงาน "การพัฒนาเกมโดยประยุกต์ใช้เทคนิค Finite State 
Machine ในการควบคุมตัวละครและปัญญาประดิษฐ์" โดยใช้ Unity Game Engine และภาษา C# 
โครงงานนี้จะมุ่งเน้นการเขียนโปรแกรมเพื่อจัดการกลไกการเคลื่อนไหวที่ซับซ้อน (Advanced 
Movement Mechanics) และระบบ AI ที่ไล่ล่าผู้เล่นอย่างเป็นระบบ เพื่อเป็นกรณีศึกษาการนำความรู้

ต่อเนื่องในเกมยุคปัจจุบัน เนื่องจาก สามารถสร้างประสบการณ์การเล่นที่ชัดเจนและเข้าใจง่าย
คุณลักษณะสำคัญของเกม Side-scrolling ได้แก่ การเคลื่อนที่ของตัวละครใน แนวแกน X เป็นหลัก 
กล้องจะเลื่อนตาม (Follow Camera) ไปพร้อมกับตัวละคร การออกแบบฉากในแนวนอนที่มีความ
ต่อเนื่อง รวมถึงการใช้ระบบชั้น (Layering) เพื่อสร้างความลึกในภาพแบบ 2 มิติ เช่น ฉากหลังเลื่อนช้า
กว่าฉากหน้า (Parallax Scrolling) ซึ่งช่วยเพิ่มความสมจริงให้กับเกม ในการพัฒนาเกม Side-scrolling 
Horror Game นั้น มุมมองด้านข้างช่วย สร้างบรรยากาศความหวาดกลัวได้อย่างมีประสิทธิภาพ 
เนื่องจากผู้เล่นจะมองเห็นสิ่งที่อยู่ ข้างหน้าและข้างหลังได้อย่างชัดเจน แต่ไม่สามารถมองเห็นสิ่งที่อยู่
ด้านบนหรือด้านล่างได้ครบถ้วน ทำให้เกิดความตื่นเต้นและความไม่แน่นอนขณะเล่น

2.5 แนวคิดเกี่ยวกับ Finite State Machine (FSM)
Finite State Machine (FSM) หรือเครื่องสถานะจำกัด เป็นแบบจำลอง และการ การคำนวณที่
ใช้กำหนดพฤติกรรมของระบบผ่านชุดของสถานะ (States) เปลี่ยนผ่านสถานะ (Transitions) ตามเงื่อนไข
ที่กำหนด โดยในช่วงเวลาใดเวลาหนึ่ง ระบบจะอยู่ได้เพียงสถานะเดียวเท่านั้น FSM เป็นที่นิยมอย่าง
กว้างขวางในการพัฒนาเกม เนื่องจากเข้าใจง่าย ใช้ทรัพยากรประมวลผลต่ำ และสามารถปรับแก้
พฤติกรรมได้โดยไม่ กระทบโครงสร้างทั้งหมด
องค์ประกอบของ FSM ได้แก่ สถานะเริ่มต้น สถานะที่เป็นไปได้ เหตุการณ์ เงื่อนไข 
และการเปลี่ยนสถานะ โครงงานใช้ FSM ในสคริปต์เพื่อกำหนดสิทธิ์การควบคุมผู้เล่นและพฤติกรรมศัตรู 
ส่วน Animator ใช้เครื่องสถานะอีกชุดหนึ่งสำหรับเลือกภาพเคลื่อนไหว 
ทั้งสองส่วนเชื่อมกันผ่านพารามิเตอร์ จึงไม่จำเป็นต้องมีชื่อหรือจำนวนสถานะเท่ากัน เช่น Normal 
รองรับทั้งการยืนและเดิน ส่วน Chase ของ Killer ส่งค่าให้เล่น Run

ทำงานร่วมกันได้อย่างเป็นระบบและสามารถปรับปรุงต่อได้

พื้นที่ เก็บกุญแจให้ครบ หลีกเลี่ยงศัตรู และเดินทางไปยังประตูทางออก โดยสามารถใช้ไฟฉาย จุดซ่อนตัว 
และก้อนหินสร้างเสียงล่อศัตรูเพื่อช่วยในการหลบหนี ขั้นตอนการดำเนินงานประกอบด้วยการกำหนด
ปัญหา การรวบรวมข้อมูล การวิเคราะห์ระบบ การออกแบบระบบ การพัฒนา การทดสอบ และการ

3.1 การกำหนดปัญหา
3.1.1 ปัญหาด้านการควบคุมตัวละครผู้เล่น

3.1.2 ปัญหาด้านพฤติกรรมของศัตรู
ศัตรูต้องตอบสนองต่อผู้เล่นได้หลายลักษณะ ทั้งการลาดตระเวน การหันหาเสียง การตรวจสอบ

ไม่สมเหตุสมผลหรือไม่สามารถกลับไปลาดตระเวนได้หลังจากสูญเสียเป้าหมาย จึงใช้ Enemy FSM 
ควบคุมลำดับการตัดสินใจจากข้อมูลการมองเห็น การได้ยิน ระดับความสงสัย และตำแหน่งล่าสุดของผู้

กิจกรรมต่าง ๆ ของผู้เล่น การวิ่งมีความสำคัญมากกว่าการเดิน ขณะที่ก้อนหินและกับดักกระจกสร้าง

3.5 การพัฒนาระบบ
3.5.1 สถาปัตยกรรมของระบบ
ระบบประกอบด้วย PlayerController, PlayerHealth, FlashlightController, 
HidingSystem, FootstepSystem, KillerAI, InventoryManager, ExitDoor, GameManager, 
UIManager, AudioManager, LevelAudioController และ Level3HeartbeatWarning โดย

ส่งเหตุการณ์เสียงให้ KillerAI ขณะที่ InventoryManager ส่งจำนวนกุญแจให้ UIManager และ 
ExitDoor ส่วน GameManager ควบคุมสถานะเกมและการเปลี่ยนฉาก
3.5.2 การพัฒนา Player FSM
Player FSM ใช้สถานะ Normal, Hidden, Frozen, Hurt, UsingItem, Transitioning และ 
Dead เพื่อควบคุมการรับคำสั่ง Normal เป็นสถานะที่อนุญาตการควบคุมทั่วไป Hidden ใช้เมื่ออยู่ในจุด
ซ่อน Frozen และ Hurt ใช้หยุดหรือจำกัดการควบคุมชั่วคราว UsingItem ป้องกันคำสั่งที่ขัดแย้งระหว่าง
ใช้ไอเท็ม Transitioning ใช้ระหว่างเปลี่ยนฉาก และ Dead ใช้เมื่อพลังชีวิตหมด
3.5.3 การพัฒนา Enemy FSM
Enemy FSM รับข้อมูลจากระบบการมองเห็นและการได้ยิน จากนั้นประเมินความสงสัยและ
เลือกสถานะ เสียง Glass และ Sprint มีความสำคัญมากกว่าเสียง Footstep ทั่วไป ศัตรูเก็บตำแหน่ง
ล่าสุดไว้ชั่วคราวเพื่อใช้ตรวจสอบและค้นหา หากไม่พบเป้าหมายจะกลับไปยังเส้นทางลาดตระเวน
3.5.4 การพัฒนาระบบความตึงเครียด

3.5.8 การพัฒนาระบบแอนิเมชันของตัวละครผู้เล่น

จึงเปลี่ยนสถานะได้ทันทีเมื่อเงื่อนไขเป็นจริง โดยไม่ต้องรอให้คลิปเดิมเล่นถึงจุดสิ้นสุด

จึงใช้สถานะการเคลื่อนที่ของผู้เล่นเป็นตัวควบคุมภาพจริง ใน Controller ปัจจุบันยังไม่มีสถานะ Run

Any State เป็นจุดสำหรับกำหนดการเปลี่ยนจากสถานะใดก็ได้ แต่ของผู้เล่นยังไม่มี Transition

3.5.11 เหตุผลในการเลือกชนิดพารามิเตอร์ของ Animator
Unity มีพารามิเตอร์ Float, Int, Bool และ Trigger เพื่อแทนข้อมูลต่างลักษณะ 
การเลือกชนิดขึ้นอยู่กับว่าเป็นค่าต่อเนื่อง รหัสสถานะ เงื่อนไขที่คงอยู่ หรือเหตุการณ์เฉพาะครั้ง 
ไม่จำเป็นต้องใช้ครบทั้งสี่ชนิดใน Controller เดียว โครงการนี้ใช้ Bool และ Trigger จริง ส่วน Float 
และ Int อธิบายเป็นทางเลือกสำหรับการขยายระบบ
Float สำหรับค่าต่อเนื่อง
Float เก็บตัวเลขที่มีทศนิยม เหมาะกับค่าความเร็ว เช่น 0, 1.5 และ 3.2 หากเพิ่มพารามิเตอร์ 
Speed จะส่งค่าด้วย SetFloat และใช้เปรียบเทียบกับเกณฑ์หรือควบคุม Blend Tree เพื่อผสมท่ายืน 
เดิน และวิ่งตามความเร็วได้ เหตุผลที่เลือก Float คือรักษารายละเอียดระหว่างค่าความเร็วซึ่ง Int 
จะเก็บไม่ได้ ปัจจุบันยังไม่มีพารามิเตอร์ Float ใน Animator ทั้งสองตัว
Int สำหรับรหัสหรือทางเลือกหลายค่า
Int เก็บจำนวนเต็ม เหมาะกับการแทนโหมดที่แยกกัน เช่น MovementMode เท่ากับ 0 
สำหรับยืน 1 สำหรับเดิน และ 2 สำหรับวิ่ง แล้วส่งค่าด้วย SetInteger เหตุผลที่เลือก Int 
คือใช้ค่าเดียวระบุทางเลือกหลายแบบ ลดการใช้ Bool หลายตัวที่อาจเป็น true พร้อมกัน อย่างไรก็ตาม 
ตัวแปร int ที่เก็บผล Animator.StringToHash เป็นเพียงรหัสอ้างอิงชื่อพารามิเตอร์ 
ไม่ได้ทำให้พารามิเตอร์นั้นเป็นชนิด Int และ Controller ปัจจุบันยังไม่ได้ใช้ Int
Bool สำหรับเงื่อนไขที่ต้องคงสถานะ
Bool มีค่า true หรือ false เหมาะกับคำถามว่ากำลังเดินหรือกำลังวิ่งหรือไม่ จึงใช้ isWalking 
ในผู้เล่น และ isWalking กับ isRunning ใน Killer โดยส่งค่าด้วย SetBool เหตุผลที่เลือก Bool 
คือระบบต้องรักษาค่าขณะพฤติกรรมยังดำเนินอยู่ และเปลี่ยนกลับเมื่อพฤติกรรมหยุด 
ทำให้การเข้าและออกจาก Walk หรือ Run ตรวจสอบได้ตรงไปตรงมา
Trigger สำหรับเหตุการณ์เฉพาะครั้ง
Trigger เหมาะกับคำสั่งเริ่มการกระทำ เช่น โจมตีหรือกรีดร้อง จึงใช้ attack1 และ scream ผ่าน 
SetTrigger เมื่อ Transition ใช้ Trigger แล้ว Controller จะรีเซ็ตค่าโดยอัตโนมัติ หากยังไม่มี 
Transition ใช้ค่านั้น อาจต้องเรียก ResetTrigger เพื่อยกเลิกคำสั่งที่ค้างอยู่ เหตุผลที่เลือก Trigger 
คือไม่ต้องเปิด Bool ค้างไว้และคอยสั่งปิดเองทุกครั้ง ส่วนการออกจากคลิปยังต้องกำหนด Transition 
และ Exit Time ให้เหมาะสม
ตรวจสอบจาก PlayerAnimator.controller, KillerAnimator.controller, 
PlayerController.cs และ KillerAI.cs ในโครงการ SideScrollingEscape ส่วนชนิดพารามิเตอร์อ้างอิง 
Unity Manual เรื่อง Animation Parameters ตามบรรณานุกรม ตรวจสอบวันที่ 4 ตุลาคม 2569

Stamina ลดลงและสร้างเสียงที่ศัตรูสามารถตรวจจับได้ ส่วนไฟฉายมีปริมาณแบตเตอรี่จำกัด ทำให้ผู้เล่น

สามารถพัฒนาส่วนติดต่อผู้ใช้งานให้แสดงข้อมูลสำคัญระหว่างเล่น ได้แก่ พลังชีวิต Stamina 
ปริมาณแบตเตอรี่ จำนวนกุญแจ ข้อความโต้ตอบ สถานะการซ่อน และคำเตือนเมื่อศัตรูอยู่ใกล้
ระบบแสดงผลจะเปลี่ยนตามสถานการณ์ เช่น แสดงข้อความแนะนำเมื่อผู้เล่นเข้าใกล้วัตถุ แสดง 
DANGER เมื่อศัตรูไล่ล่า แสดง Game Over เมื่อผู้เล่นเสียชีวิต และแสดง Level Complete หรือ 
Game Won เมื่อผู้เล่นผ่านเงื่อนไขของด่าน
5.1.7 อภิปรายผลการพัฒนา
ผลการพัฒนาแสดงให้เห็นว่า Finite State Machine เหมาะสำหรับระบบที่ประกอบด้วย
พฤติกรรมหลายสถานะและมีเงื่อนไขการเปลี่ยนสถานะที่ชัดเจน เนื่องจากช่วยแยกหน้าที่ของแต่ละ
สถานะ ลดความซับซ้อนของการตรวจสอบเงื่อนไข และช่วยให้สามารถติดตามพฤติกรรมของระบบได้ง่าย
ขึ้น
ผลดังกล่าวสอดคล้องกับหลักการของ FSM ที่กำหนดให้ระบบอยู่ในสถานะหนึ่ง ณ ช่วงเวลาหนึ่ง 
และเปลี่ยนไปยังสถานะใหม่เมื่อเกิดเหตุการณ์หรือเป็นไปตามเงื่อนไขที่กำหนด การนำแนวคิดนี้มาใช้กับผู้
เล่นช่วยป้องกันคำสั่งที่ขัดแย้งกัน ส่วนการใช้กับศัตรูช่วยให้กระบวนการลาดตระเวน ตรวจจับ ค้นหา ไล่
ล่า และโจมตีมีลำดับที่ชัดเจน
การใช้ระบบตรวจจับด้วยเสียงร่วมกับ FSM ช่วยเพิ่มความหลากหลายของพฤติกรรมศัตรู 
เนื่องจากศัตรูไม่จำเป็นต้องมองเห็นผู้เล่นโดยตรงจึงจะตอบสนองได้ อย่างไรก็ตาม ความสมจริงของศัตรู
ยังขึ้นอยู่กับการกำหนดค่าความเร็ว ระยะตรวจจับ ระยะเวลาของแต่ละสถานะ และรูปแบบพื้นที่ภายใน
ด่าน หากกำหนดค่าไม่เหมาะสม เกมอาจง่ายหรือยากเกินไป
การแบ่งระบบออกเป็นส่วนย่อย เช่น PlayerController, KillerAI, InventoryManager, 
ExitDoor, GameManager, UIManager และระบบเสียงของด่าน 
ช่วยให้สามารถปรับปรุงแต่ละระบบได้โดยไม่กระทบส่วนอื่นมากเกินไป 
และช่วยให้ตรวจสอบข้อผิดพลาดได้สะดวกกว่าการรวมการทำงานทั้งหมดไว้ในสคริปต์เดียว 
ระบบความตึงเครียดยังใช้ TensionDirector ที่ประกาศในไฟล์ LevelAudioController.cs 
เพื่อรวมสถานะศัตรูและแจ้งระบบเสียง

5.1.8 สถานะการบรรลุวัตถุประสงค์
ด้านการพัฒนาซอฟต์แวร์ มีต้นแบบและโครงสร้าง FSM ของผู้เล่นและศัตรู พร้อม Animator 
ที่อธิบายในบท 3 และผลตรวจในบท 4 ด้าน Gameplay Loop มีเมธอดและหน้าจอผ่านด่าน 
แต่ยังต้องเล่นทดสอบต่อเนื่องทุกด่านเพื่อยืนยัน ด้านการประเมินความพึงพอใจยังไม่บรรลุ 
เนื่องจากยังไม่ได้เก็บแบบสอบถาม ตัวอย่างข้อมูลสมมติในภาคผนวกใช้สอนวิธีคำนวณเท่านั้น
5.2 ปัญหาที่พบในโครงงาน
5.2.1 ปัญหาการเปลี่ยนสถานะของ FSM
ในระหว่างการพัฒนา 
มีความเสี่ยงว่าบางสถานการณ์ทำให้ระบบพยายามเปลี่ยนสถานะมากกว่าหนึ่งครั้งในเวลาใกล้เคียงกัน 
เช่น ผู้เล่นได้รับความเสียหายขณะเปิดกระเป๋า ถูกศัตรูโจมตีระหว่างปลดล็อกประตู 
หรือศัตรูได้ยินเสียงพร้อมกับมองเห็นผู้เล่น 
ปัญหานี้อาจทำให้คำสั่งบางอย่างทำงานซ้อนกันหรือระบบเปลี่ยนไปยังสถานะที่ไม่เหมาะสม
แนวทางแก้ไขคือกำหนดลำดับความสำคัญของสถานะ ตรวจสอบสถานะปัจจุบันก่อนรับคำสั่ง 
และจำกัดให้แต่ละระบบเปลี่ยนสถานะผ่านฟังก์ชันส่วนกลาง เช่น SetPlayerState() หรือ SetState() 
เพื่อให้สามารถควบคุมการเปลี่ยนสถานะได้จากตำแหน่งเดียว
5.2.2 ปัญหาการตรวจจับของศัตรู
ระบบการมองเห็นของศัตรูอาจตรวจจับผิดพลาดเมื่อผู้เล่นอยู่ใกล้ขอบสิ่งกีดขวาง หรือเมื่อ 
Collider ของวัตถุไม่ตรงกับภาพที่แสดงในฉาก 
ส่วนระบบการได้ยินอาจทำให้ศัตรูตอบสนองต่อเสียงหลายเหตุการณ์พร้อมกัน 
จนเกิดการเปลี่ยนเป้าหมายบ่อยเกินไป
แนวทางแก้ไขคือปรับ LayerMask และ Collider ให้ตรงกับวัตถุ ตรวจสอบแนว Raycast ที่ใช้
ในการมองเห็น และกำหนดระดับความสำคัญของเสียง ศัตรูจะเลือกตรวจสอบเสียงที่มีความสำคัญ
มากกว่าหรือเสียงที่เกิดขึ้นล่าสุด พร้อมเก็บตำแหน่งเสียงไว้เพียงช่วงเวลาที่กำหนด
5.2.3 ปัญหาการเคลื่อนที่ของศัตรูในฉากสองมิติ
ศัตรูอาจติดขอบพื้น สิ่งกีดขวาง หรือพื้นที่ต่างระดับ โดยเฉพาะฉากที่ประกอบจาก Tilemap 
หลายชั้น หากจุดลาดตระเวนอยู่ในตำแหน่งที่ศัตรูเดินไม่ถึง 
ระบบอาจพยายามเคลื่อนที่ไปยังเป้าหมายเดิมอย่างต่อเนื่อง

แนวทางแก้ไขคือกำหนดเส้นทางลาดตระเวนให้สอดคล้องกับพื้นที่ที่เดินได้ ตรวจสอบพื้นและ
ขอบทางเดินก่อนเปลี่ยนทิศทาง รวมถึงกำหนดเงื่อนไขให้ศัตรูกลับไปยังจุดลาดตระเวนที่เหมาะสมเมื่อไม่
สามารถเดินทางไปยังเป้าหมายเดิมได้
5.2.4 ปัญหาการสุ่มตำแหน่งวัตถุใน Level 3
การสุ่มตำแหน่งกุญแจและกับดักอาจทำให้วัตถุปรากฏซ้อนกัน อยู่ใกล้กันเกินไป หรืออยู่ใน
ตำแหน่งที่ผู้เล่นไม่สามารถเข้าถึงได้ หากสุ่มโดยใช้พิกัดทั่วไปโดยไม่ตรวจสอบพื้นภายในฉาก
แนวทางแก้ไขคือให้ Level3RandomEvents 
เลือกตำแหน่งจากพื้นที่ที่ตรวจสอบแล้วว่าสามารถเดินได้ กำหนดระยะห่างขั้นต่ำระหว่างวัตถุ 
และแยกจุดสุ่มของกุญแจกับกับดัก เพื่อลดโอกาสที่วัตถุหลายชิ้นจะรวมอยู่ในบริเวณเดียวกัน
5.2.5 ปัญหาการปรับสมดุลระดับความยาก
ค่าความเร็ว ระยะการมองเห็น ระยะการได้ยิน และความเสียหายของศัตรูมีผลต่อความยากอย่าง
มาก หากเพิ่มหลายค่าพร้อมกัน ผู้เล่นอาจไม่มีเวลาเพียงพอสำหรับหลบหนีหรือหาจุดซ่อน โดยเฉพาะ 
Level 3 ซึ่งกำหนดให้ศัตรูมีความเร็วและระยะการได้ยินสูง
แนวทางแก้ไขคือแยกค่าความยากของแต่ละด่านไว้ใน LevelConfig 
และปรับค่าทีละส่วนจากผลการทดลองเล่น เช่น ปรับความเร็วไล่ล่า ระยะได้ยิน เวลาค้นหา 
และจำนวนจุดซ่อน เพื่อหาค่าที่สร้างความกดดันโดยยังเปิดโอกาสให้ผู้เล่นสามารถผ่านด่านได้
5.2.6 ปัญหาการจัดวางกล้องและองค์ประกอบของด่าน
กล้องอาจอยู่ต่ำหรือสูงเกินไป 
ทำให้ไม่สามารถมองเห็นเส้นทางและองค์ประกอบสำคัญของด่านได้ครบถ้วน นอกจากนี้ 
การใช้ขอบเขตกล้องร่วมกันกับด่านที่มีขนาดแตกต่างกันอาจทำให้เกิดพื้นที่ว่างนอกฉากหรือทำให้วัตถุบาง
ส่วนอยู่นอกหน้าจอ
แนวทางแก้ไขคือกำหนดตำแหน่งและขอบเขตกล้องแยกตามแต่ละด่าน ปรับค่าแกนตั้งของกล้อง
ให้เหมาะกับระดับพื้น และทดสอบบริเวณขอบซ้าย ขอบขวา พื้นที่ชั้นบน และพื้นที่ชั้นล่างก่อนสรุปการ
จัดวางด่าน
5.2.7 ปัญหาการทำงานร่วมกันของหลายระบบ

5.2.8 สิ่งที่ได้เรียนรู้จากการพัฒนา
ผู้พัฒนาได้เรียนรู้ว่าการออกแบบโครงสร้างระบบก่อนเขียนโปรแกรมช่วยลดการแก้ไขโค้ดใน

ถูกต้องตามโค้ดอาจยังไม่ให้ประสบการณ์ที่เหมาะสม เช่น ศัตรูอาจเร็วเกินไป คำเตือนอาจไม่ชัดเจน หรือ
การจัดวางวัตถุอาจทำให้ผู้เล่นไม่เข้าใจเส้นทาง ดังนั้นผลจากผู้ทดลองเล่นจึงควรถูกนำมาใช้ร่วมกับการ

5.3 ข้อเสนอแนะ
5.3.1 ข้อเสนอแนะสำหรับการนำระบบไปใช้
ก่อนนำเกมไปใช้งานหรือเผยแพร่ ควรทดสอบกรณีทดสอบทั้งหมดและบันทึกผลที่เกิดขึ้นจริง 
โดยเฉพาะการเปลี่ยนสถานะของผู้เล่นและศัตรู การตรวจจับเสียง การปลดล็อกประตู และการผ่าน 
Level 3 ไม่ควรสรุปว่าระบบสมบูรณ์จากการตรวจสอบโค้ดเพียงอย่างเดียว
ควรทดสอบกับอุปกรณ์ที่มีประสิทธิภาพแตกต่างกัน ตรวจสอบอัตราเฟรม ความละเอียดหน้าจอ 
ตำแหน่ง UI และการตอบสนองของปุ่มควบคุม เนื่องจากผลการทำงานอาจแตกต่างกันตามขนาดหน้าจอ
และความสามารถของอุปกรณ์
การปรับค่าความยากผ่าน LevelConfig ควรดำเนินการอย่างระมัดระวัง เพราะความเร็ว ระยะ
ตรวจจับ ความเสียหาย และทรัพยากรเริ่มต้นมีผลต่อกัน หากต้องการปรับความยากควรเปลี่ยนค่าทีละ
ส่วนและทดลองเล่นซ้ำก่อนนำไปใช้จริง
5.3.2 ข้อเสนอแนะสำหรับการพัฒนาระบบเพิ่มเติม
ควรเพิ่มรูปแบบพฤติกรรมของศัตรูให้หลากหลาย เช่น การตรวจสอบจุดซ่อน การคาดเดา
เส้นทางของผู้เล่น การตอบสนองร่วมกันของศัตรูหลายตัว และการจดจำพื้นที่ที่พบผู้เล่นบ่อย เพื่อให้การ
เล่นแต่ละรอบไม่สามารถคาดเดาได้ง่าย
ควรเพิ่มความหลากหลายของไอเท็ม เช่น ไอเท็มฟื้นฟูพลังชีวิต แบตเตอรี่สำรอง อุปกรณ์สร้าง
เสียงล่อศัตรู หรือไอเท็มป้องกันการโจมตีชั่วคราว โดยต้องกำหนดข้อจำกัดเพื่อไม่ให้ไอเท็มลดความน่า
